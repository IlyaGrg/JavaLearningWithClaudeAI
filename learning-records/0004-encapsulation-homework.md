# Инкапсуляция: защиты написаны верно, «тот же счёт» проверяет через имя и `==`

Домашку 0003 Илья сделал сам и полностью: все поля `private`, проверки до присваивания, вынес их в `private static` методы `checkX` (шаблон из урока перенёс на новые поля без подсказки). Сеттер есть только у цены, у баланса нет. Каждую защиту проверил отдельно и записал сообщения и ошибку компиляции `balance has private access`. Предсказание `b = a; b.withdraw(300)` → 700 верное. Алиасинг на объектах закреплён (интервальное повторение после урока 2 пройдено).

**Evidence**: `src/lesson0003/`, коммиты 23117c0, f522a98, 83e8967; ревью 2026-10-10 (запуск на JDK 21 + граничные случаи).

**Implications**:
- **Пробел**: в `transferTo` «перевод самому себе» проверяется как `other.owner == owner`. Две ошибки сразу: сравнивает людей, а не счета (перевод между двумя счетами одного владельца запрещён), и сравнивает строки через `==`. С литералами это работает случайно: `new String("Илья")` проходит проверку. Нужное понятие: `==` на объектах сравнивает ссылки, `this` — «этот самый объект». Тема `==` против `equals` нужна до коллекций (Map/Set).
- `transferTo` дублирует проверки `withdraw`, а не переиспользует его. При этом снимать 0 можно, пополнять на 0 нельзя: `transferTo(x, 0)` падает с сообщением из `deposit`. Хороший вход в тему урока 4: порядок «сначала все проверки, потом изменения» и атомарность операции.
- Строку стека для каждой защиты не записал, только сообщения. Чтение стека проверить в уроке 4.
- Объяснение «почему нет setBalance» поверхностное («нельзя выставить большую сумму»). Хорошо бы, чтобы он сформулировал: любое изменение баланса должно идти через операцию с правилами.
