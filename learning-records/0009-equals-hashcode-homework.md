# equals/hashCode: шаблон и договор усвоены; при переделке Bank потеряны проверки

В домашке 0008 Илья руками написал `equals(Object)` / `hashCode` для `AccountNumber` по шаблону: `this == o`, `null` и `getClass`, приведение типа, `equals` для строки, `Objects.hash`. Своими словами объяснил разницу «объект-значение — сущность». Все 6 строк предсказания про `Integer` и `String` верны, с причиной («>127»). **Сам выполнил упражнение «сломай — посмотри, какой тест упал»**: без `hashCode` падают проверки 2, 3, 4, а 1 и 5 проходят. Я проверил — совпадает, и в комментариях объяснено через хеш. Эксперимент с изменяемым `hashCode` у счёта сделан: `contains` → `false`, объяснение верное.

**Evidence**: `src/lesson0008/`, коммиты 5eb84cb, f9bd41f; ревью 2026-10-16, JDK 21.

**Implications**:
- **Пробел (регрессия)**: в задании было «проверки *пустого номера* можно убрать». Он убрал **все** проверки банка. `findAccount` несуществующего номера снова возвращает `null` вместо `AccountNotFoundException`. `openAccount(null, …)` и `openAccount(номер, null)` проходят, потом в `totalBalance` — NPE. Проверки 3–5 из урока 7 в новый `Main` не перенесены, поэтому регрессию никто не поймал. Хорошая иллюстрация, зачем нужен постоянный набор тестов (JUnit).
- `equals`/`hashCode` по владельцу и балансу, добавленные в `BankAccount` для эксперимента 4.2, **не удалены**, хотя урок прямо объясняет, почему счёту они вредны. Плюс двойная проверка `o == null`.
- Проверка 3 сравнивает `findAccount(first) == findAccount(second)`. Она пройдёт и если оба вернут `null`, надёжнее сравнивать с самим счётом.
- Эксперимент 4.1, вторая часть (что покажут проверки без `@Override`), не записан. Сообщение «Некорректное значение: » без значения. Косметика: пробелы перед `{`, `}\nelse{`.

**Update (ревью 2026-10-17, не закоммичено)**: `equals`/`hashCode` из `BankAccount` удалены. Проверки банка возвращены (null-номер, null-счёт, несуществующий номер → `AccountNotFoundException`), к ним добавлены 3 проверки через `check`, все 8 — ОК. Проверка 3 теперь сравнивает с `ilyaAccount`. Остались: `checkNumber` повторяет `isBlank`/`startsWith` из конструктора `AccountNumber`. Идея «инвариант гарантирует конструктор, не-null номер всегда корректен» не применена, хотя это и был ответ на вопрос «почему проверки можно убрать». `transfer` не использует `findAccount`: несуществующий получатель даёт вводящее в заблуждение «несуществующему пользователю», несуществующий отправитель — NPE (проверено). Нет проверки дубликата номера. Попросил подробно объяснить эксперимент 4.1 (перегрузка `equals(AccountNumber)` без `@Override`). Объяснено через выбор перегрузки компилятором по типу аргумента; проверено: прямой вызов `true`, через `Object` `false`, `HashSet` 2, `HashMap.get` `null`, `List.contains` `false`, его `Main` падает на проверке 3 с `AccountNotFoundException`.

**Закрыто (ревью 2026-10-17, не закоммичено)**: `checkNumber` сокращён до проверки `null`, то есть понял, что инвариант держит конструктор `AccountNumber`. `transfer` идёт через `findAccount`. Проверка дубликата номера добавлена (но с тем же объектом, а не с равным). Эксперимент 4.1 объяснил своими словами по каждой проверке верно: 1 — вызвана перегрузка, 2 — hashCode на месте, 3–4 — коллекции вызывают `equals(Object)`, 5 — `null` попадает в перегрузку. Все 8 проверок ОК. Хвост: проверка 3 осталась **закомментированной** после эксперимента — ровно та, что ловит главный баг урока. Повторяющийся паттерн: после экспериментов не откатывает код полностью (было и с `BankAccount.equals`). README обновлён, глоссарий пополнен.
