Разминка: синтаксис по памяти

Ты сказал, что теорию понимаешь, а синтаксис пишется с трудом. Это лечится только одним: писать по памяти. Перед каждым ответом напиши код на бумаге или в редакторе, потом открой.

1. Запиши запись Money с компонентами int amount и Currency currency, которая не даёт создать отрицательную сумму. 
public record Money(int amount, Currency currency) {
    public Money {                                   // компактный: без (int amount, ...)
        if (amount < 0) {
            throw new IllegalArgumentException("Сумма меньше нуля: " + amount);
        }
    }
}

Три места, где обычно ошибаются: компоненты — в круглых скобках после имени, как параметры метода; у компактного конструктора нет скобок с параметрами; внутри нет this.amount = amount — его допишет Java.

2. Лямбда-Predicate<BankAccount>: «владелец — Ilya и баланс больше 1000». Запиши в переменную. 
Predicate<BankAccount> rich = acc -> acc.getOwner().equals("Ilya") && acc.getBalance() > 1000;

Как собрать лямбду по шагам: (1) какой метод интерфейса реализуем? boolean test(BankAccount t). (2) Слева от -> — имя параметра (любое, тип Java знает из Predicate<BankAccount>). (3) Справа — то, что метод вернул бы через return, без самого return и без ; внутри.

3. Достань счёт из Optional<BankAccount> found или брось AccountNotFoundException. 
BankAccount acc = found.orElseThrow(() -> new AccountNotFoundException("Нет счёта"));

() -> — лямбда без параметров (Supplier): «вот как создать исключение, если понадобится».

1. Какую проблему решает Maven

Вспомни, как ты сейчас запускаешь банк:

javac -d out src/lesson0013/*.java
java -cp out lesson0013.Main

Это работает, пока проект маленький. Но у этого способа три дыры:

  1. Чужой код подключить нельзя. Захочешь библиотеку (JUnit для тестов, драйвер PostgreSQL, Spring) — придётся самому скачать .jar-файл с сайта, положить в папку, вписать в -cp. А у библиотеки свои библиотеки, у тех свои… У Spring Boot их десятки.
  2. Сборку знаешь только ты. Другой разработчик клонирует репозиторий и не знает, какую версию Java брать, какие файлы компилировать, где главный класс. Настройки IntelliJ (.idea/) ты в Git не кладёшь — и правильно.
  3. Каждый раскладывает файлы по-своему. Где код, где тесты, куда класть результат — договариваться в каждом проекте заново.

Maven — программа, которая собирает Java-проекты по описанию из одного файла pom.xml (Apache Maven: What is Maven). В этом файле ты пишешь что собрать: имя проекта, версию Java, нужные библиотеки. Как собирать — Maven знает сам: где искать код, в каком порядке компилировать, куда положить результат.

Как в Python. pom.xml — это requirements.txt и pyproject.toml в одном файле: «какие библиотеки каких версий нужны». mvn — как pip install, только он ещё и компилирует, запускает тесты и упаковывает. Библиотеки Maven скачивает с Maven Central — это как PyPI для Java. Отличие: виртуальное окружение не нужно — каждый проект сам говорит, какие версии ему нужны, и Maven подставляет их при сборке.

3. XML за десять минут

pom.xml написан на XML — формате, где данные лежат внутри тегов, как в HTML. Если ты видел HTML — ты почти всё знаешь. Правил пять:

шаблон элемента XML

<имя>значение</имя>
  1. Каждый открытый тег закрывается тегом с тем же именем и косой чертой: <version>1.0</version>.
  2. Теги вкладываются, как матрёшки, и закрываются в обратном порядке. Внутри тега может быть либо текст, либо другие теги: 
    <dependency>                         ← открыли внешний
    <groupId>org.apache.commons</groupId>   ← внутренний: открыли и закрыли
    <version>3.17.0</version>
</dependency>                        ← закрыли внешний
  3. Регистр важен: <artifactId> и <artifactid> — разные теги. Как в Java: count и Count.
  4. Отступы ни на что не влияют (в отличие от Python), но без них ты сам запутаешься. Принято 4 пробела на уровень.
  5. Комментарий: <!-- текст -->.

Что бывает, если нарушить. Я написал <artifactId>bank</artifactid> (маленькая i в закрывающем):

[FATAL] Non-parseable POM .../pom.xml: end tag name </artifactid> must be the same as start tag <artifactId> from line 8

А тут я случайно вставил второй блок <build>, хотя он уже был:

[FATAL] Non-parseable POM .../pom.xml: Duplicated tag: 'build' ... @ line 37, column 12

Слово Non-parseable значит «Maven даже не смог прочитать файл» — ошибка в самом XML, а не в Java. Ищи строку и колонку, которые он назвал.

4. pom.xml — пишем с нуля по шагам

POM — Project Object Model, «описание проекта» (Apache Maven: POM Reference). Сейчас мы напишем его в четыре шага; после каждого шага файл уже рабочий. Именно в таком порядке ты будешь писать его в домашке.

  1. Скелет и «паспорт» проекта. Это минимальный pom.xml, с которым Maven уже работает.

    <?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>ru.ilyagrg</groupId>
    <artifactId>bank</artifactId>
    <version>1.0-SNAPSHOT</version>
</project>
    <?xml version="1.0" encoding="UTF-8"?>
    заголовок любого XML-файла: «я XML, кодировка UTF-8». Пишется один раз, первой строкой, всегда одинаково
    <project xmlns=... >
    корневой тег — всё остальное внутри него. Атрибуты xmlns и schemaLocation говорят IntelliJ, по какой схеме проверять файл, — тогда она подсказывает теги. Эти три строки не запоминай, копируй: так делают все, в том числе start.spring.io
    <modelVersion>4.0.0</modelVersion>
    версия формата POM. Всегда 4.0.0, просто пиши
    <groupId>ru.ilyagrg</groupId>
    кто делает проект: перевёрнутый домен автора или компании (org.apache.commons, org.springframework). Своего домена нет — бери ru. + ник с GitHub
    <artifactId>bank</artifactId>
    что за проект: короткое имя маленькими буквами, через дефис (console-bank). Так будет назван итоговый .jar
    <version>1.0-SNAPSHOT</version>
    какая версия. SNAPSHOT — «в разработке, ещё меняется». Готовый выпуск — 1.0 без суффикса

    Тройка groupId:artifactId:version называется координатами (GAV). По ним любой проект в мире однозначно находится — и твой, и Spring. Запомни это слово: в шаге 3 ты будешь писать координаты чужого проекта.

  2. Настройки сборки — <properties>. Добавляем после <version>, внутри <project>:

        <properties>
        <maven.compiler.release>21</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>
    <properties>
    блок «переменных»: имя тега — имя настройки, текст — значение
    maven.compiler.release = 21
    компилировать под Java 21. Это то же, что javac --release 21
    project.build.sourceEncoding = UTF-8
    файлы .java в UTF-8. Иначе на чужой машине твои «ОШИБКА» и «Российский рубль» могут превратиться в кракозябры

    Что будет без <properties> — я убрал блок и собрал твой банк:

    [WARNING] File encoding has not been set, using platform encoding UTF-8, i.e. build is platform dependent!
[WARNING] source value 8 is obsolete and will be removed in a future release
[ERROR] .../AccountNumber.java:[5,8] records are not supported in -source 8
[ERROR] .../Currency.java:[17,16] switch expressions are not supported in -source 8

    По умолчанию Maven компилирует как Java 8 (2014 год): ни record, ни switch-выражений. Строка maven.compiler.release обязательна в каждом проекте.

  3. Зависимость — чужая библиотека. Ещё один блок внутри <project>, после <properties>:

    шаблон зависимости

        <dependencies>
        <dependency>
            <groupId>кто сделал</groupId>
            <artifactId>что за библиотека</artifactId>
            <version>какая версия</version>
        </dependency>
        … следующий <dependency> — рядом, внутри того же <dependencies>
    </dependencies>

    Заполняем для библиотеки Apache Commons Lang — в ней сотни мелких полезных методов для строк и чисел:

        <dependencies>
        <dependency>
            <groupId>org.apache.commons</groupId>
            <artifactId>commons-lang3</artifactId>
            <version>3.17.0</version>
        </dependency>
    </dependencies>

    Заметь: <dependencies> (мн. число) — коробка, <dependency> (ед.) — одна библиотека в ней. Коробка одна на весь файл. Вторую библиотеку кладёшь в ту же коробку, а не создаёшь новую — иначе получишь Duplicated tag: 'dependencies'.

    Откуда брать координаты. Не придумывать и не писать по памяти. Открываешь central.sonatype.com, ищешь commons-lang3, открываешь нужную версию — справа готовый блок <dependency> для Maven. Копируешь целиком. Так делают все.

  4. Плагин — чтобы запускать программу. Сам Maven умеет компилировать и упаковывать, а запускать main — нет. Это делает плагин — дополнение к Maven, которое тоже подключается по координатам (MojoHaus: Exec Maven Plugin). Блок <build> — последним внутри <project>:

        <build>
        <plugins>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.5.0</version>
                <configuration>
                    <mainClass>ru.ilyagrg.bank.Main</mainClass>
                </configuration>
            </plugin>
        </plugins>
    </build>
    <build><plugins>
    та же схема «коробка — элементы», что у зависимостей: <plugins> — коробка, <plugin> — один плагин
    groupId / artifactId / version
    координаты плагина — точно как у библиотеки
    <configuration>
    настройки именно этого плагина. У каждого плагина свои, они описаны в его документации
    <mainClass>ru.ilyagrg.bank.Main</mainClass>
    полное имя класса с main: пакет + точка + имя класса. Как в java -cp out lesson0013.Main

Итог — весь файл целиком, в правильном порядке блоков:

<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>ru.ilyagrg</groupId>           ← шаг 1: кто
    <artifactId>bank</artifactId>          ←          что
    <version>1.0-SNAPSHOT</version>        ←          какая версия

    <properties>                           ← шаг 2: настройки
        <maven.compiler.release>21</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>                         ← шаг 3: библиотеки
        <dependency>
            <groupId>org.apache.commons</groupId>
            <artifactId>commons-lang3</artifactId>
            <version>3.17.0</version>
        </dependency>
    </dependencies>

    <build>                                ← шаг 4: плагины
        <plugins>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.5.0</version>
                <configuration>
                    <mainClass>ru.ilyagrg.bank.Main</mainClass>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>

Пометки «← шаг» — для урока, в настоящий файл их не пиши (это не XML-комментарии, Maven на них упадёт). Файл собран и запущен на JDK 21 и Maven 3.9.

Проверь себя: какая из трёх тройок координат здесь — твоя, а какие — чужие? И почему у плагина тоже есть координаты?

Твоя — ru.ilyagrg:bank:1.0-SNAPSHOT, она описывает сам проект. Чужие — org.apache.commons:commons-lang3:3.17.0 и org.codehaus.mojo:exec-maven-plugin:3.5.0. Плагин — тоже чей-то Maven-проект, лежит на том же Maven Central, поэтому находится так же.

5. Структура папок: Maven ищет код в одном месте

Maven не спрашивает, где лежат файлы, — он ожидает их в стандартных местах (Apache Maven: Standard Directory Layout). Это и есть «соглашение вместо настройки»: в любом Maven-проекте в мире код лежит там же.

lesson0014/                         ← корень проекта: здесь pom.xml и отсюда запускаешь mvn
├── pom.xml
├── src/
│   ├── main/
│   │   └── java/                   ← корень пакетов основного кода
│   │       └── ru/ilyagrg/bank/    ← пакет ru.ilyagrg.bank
│   │           ├── Main.java
│   │           ├── Bank.java
│   │           └── ...
│   └── test/
│       └── java/                   ← тесты (урок 15), пока пусто
└── target/                         ← сюда Maven кладёт результат; создаётся сам

Пакет = путь к папке

Это правило ты уже знаешь (package lesson0013; → папка lesson0013/), но теперь пакет длиннее. Точки в имени пакета — это вложенные папки, считая от src/main/java:

package ru.ilyagrg.bank;
первая строка каждого файла
src/main/java/ru/ilyagrg/bank/Bank.java
где лежит файл. src/main/java в пакет не входит
ru.ilyagrg.bank.Main
полное имя класса — для <mainClass>

Почему пакет вида ru.ilyagrg.bank, а не просто bank? По той же причине, что и groupId: чтобы твой класс Bank не столкнулся с чужим Bank из какой-нибудь библиотеки. Обычно пакет = groupId + artifactId. Spring Initializr делает так же.

Создать все папки одной командой (флаг -p создаёт и промежуточные):

mkdir -p lesson0014/src/main/java/ru/ilyagrg/bank lesson0014/src/test/java

Ловушка: файлы не там — и Maven молчит

Я положил Main.java прямо в src/, а не в src/main/java/.... Ошибки нет:

[INFO] Building bank 1.0-SNAPSHOT
[INFO] No sources to compile
[INFO] BUILD SUCCESS

«Собрал успешно» — ноль файлов. Если видишь No sources to compile, а файлы есть — они лежат не в той папке. Это та же ловушка, что allMatch на пустом: «успех», потому что проверять было нечего.

6. Команды и жизненный цикл

Команды запускаются из папки, где лежит pom.xml. Сделал cd lesson0014 — потом mvn ....

У Maven есть жизненный цикл — фиксированная цепочка этапов (фаз) сборки (Apache Maven: Introduction to the Build Lifecycle). Главное правило: вызываешь фазу — выполняются все фазы до неё.

validate → compile → test → package → verify → install
mvn compile
скомпилировать src/main/java в target/classes. Это твой javac -d out ...
mvn test
compile + скомпилировать тесты + запустить их. Сейчас тестов нет: No tests to run. С урока 15 — главная команда
mvn package
compile + test + упаковать в target/bank-1.0-SNAPSHOT.jar. Если хоть один тест упал — jar не соберётся
mvn clean
удалить target/ целиком. Отдельный цикл; часто пишут вместе: mvn clean package — «собери с чистого листа»
mvn compile exec:java
фаза compile, потом цель плагина exec с именем java: запустить mainClass. Через двоеточие — «плагин:что сделать»

Вот что на самом деле печатает mvn clean package (лишнее убрал):

[INFO] --------------------------< ru.ilyagrg:bank >---------------------------
[INFO] Building bank 1.0-SNAPSHOT
[INFO] --- clean:3.2.0:clean (default-clean) @ bank ---
[INFO] --- resources:3.4.0:resources (default-resources) @ bank ---
[INFO] --- compiler:3.15.0:compile (default-compile) @ bank ---
[INFO] --- resources:3.4.0:testResources (default-testResources) @ bank ---
[INFO] --- compiler:3.15.0:testCompile (default-testCompile) @ bank ---
[INFO] --- surefire:3.5.4:test (default-test) @ bank ---
[INFO] --- jar:3.5.0:jar (default-jar) @ bank ---
[INFO] Building jar: .../target/bank-1.0-SNAPSHOT.jar
[INFO] BUILD SUCCESS

Прочитай построчно: в первой строке — твои координаты. Дальше каждая строка --- плагин:версия:цель --- — это один этап. Видно, что ты попросил только package, а Maven сам прошёл compile и test. Компилирует плагин compiler, тесты гоняет surefire, упаковывает jar — Maven сам по себе почти ничего не умеет, всё делают плагины. Эти стандартные плагины подключены по умолчанию, писать их в pom.xml не нужно.

Первый запуск — долгий. Maven напечатает десятки строк Downloading from central: https://repo.maven.apache.org/... — он качает плагины и библиотеки. Нужен интернет. Второй запуск — за секунды.

Ошибка компиляции в Maven

Это тот же javac, просто в другой обёртке. Я убрал закрывающую скобку в println:

[ERROR] COMPILATION ERROR :
[ERROR] .../src/main/java/ru/ilyagrg/bank/Main.java:[7,67] ')' or ',' expected
[ERROR] Failed to execute goal org.apache.maven.plugins:maven-compiler-plugin:3.15.0:compile ...

[7,67] — строка 7, символ 67. Текст после — обычное сообщение javac. Длинные строки Failed to execute goal и [Help 1] ниже — просто «сборка остановилась», причину ищи выше, в первой строке [ERROR] с именем файла.

7. Как работают зависимости

Ты написал в pom.xml координаты commons-lang3. При сборке Maven:

  1. смотрит в локальное хранилище на твоём компьютере — папку ~/.m2/repository;
  2. нет там — скачивает с Maven Central и кладёт туда: ~/.m2/repository/org/apache/commons/commons-lang3/3.17.0/commons-lang3-3.17.0.jar (видишь — путь собран из координат, точки стали папками);
  3. добавляет этот .jar в -cp компилятора — сам, тебе писать ничего не надо.

Скачивается один раз на компьютер: следующий проект с той же версией возьмёт её из ~/.m2 (Apache Maven: Dependency Mechanism).

Использование: import и вызов

После того как зависимость в pom.xml, её классы доступны как свои — нужен только import. Пример: в AccountNumber у тебя проверка value == null || value.isBlank(). В Commons Lang есть метод, который делает обе проверки сразу:

import org.apache.commons.lang3.StringUtils;          // пакет + класс из библиотеки

StringUtils.isBlank(null)     // true  — null не падает с NPE
StringUtils.isBlank("")       // true
StringUtils.isBlank("   ")    // true  — одни пробелы
StringUtils.isBlank("BANK-1") // false
org.apache.commons.lang3
пакет. Как его узнать: в документации класса (StringUtils javadoc) он написан над именем класса. Или IntelliJ: пишешь StringUtils → Alt+Enter → Import class
StringUtils.isBlank(value)
static-метод: вызывается через имя класса, объект не нужен (урок 2) — как Math.max

Две ошибки, которые ты увидишь

Забыл зависимость в pom.xml, а import написал:

[ERROR] .../Main.java:[3,32] package org.apache.commons.lang3 does not exist
[ERROR] .../Main.java:[7,41] cannot find symbol

Опечатка в координатах (я написал версию 3.99.0, которой не существует):

[ERROR] Failed to execute goal on project bank: Could not resolve dependencies for project ru.ilyagrg:bank:jar:1.0-SNAPSHOT
[ERROR] dependency: org.apache.commons:commons-lang3:jar:3.99.0 (compile)

Отличай: первая — ошибка Java (COMPILATION ERROR, есть имя файла и строка), вторая — ошибка Maven (Could not resolve dependencies, до компиляции даже не дошло).

8. Почему не java -jar: эксперимент

Эксперименты в домашке мы больше не делаем — вот результат, я запустил сам. Сначала угадай ответ к каждому пункту.

8.1. Запустить скомпилированное по-старому:

mvn compile
java -cp target/classes ru.ilyagrg.bank.Main
Exception in thread "main" java.lang.NoClassDefFoundError: org/apache/commons/lang3/StringUtils
	at ru.ilyagrg.bank.Main.main(Main.java:7)
Caused by: java.lang.ClassNotFoundException: org.apache.commons.lang3.StringUtils

Компиляция прошла — Maven сам подставил библиотеку в -cp. А java ты запускаешь руками, и в -cp только target/classes: твои классы есть, StringUtils — нет. Это ошибка при выполнении (как get() на пустом Optional), компилятор её не видит. mvn exec:java подставляет зависимости сам — поэтому запускаем через него.

8.2. Запустить собранный jar:

mvn package
java -jar target/bank-1.0-SNAPSHOT.jar
no main manifest attribute, in target/bank-1.0-SNAPSHOT.jar

В jar не записано, какой класс главный. А если записать — упадёт как в 8.1: обычный jar содержит только твои классы, библиотеки в него не входят. Spring Boot решает обе проблемы своим плагином: собирает «толстый» jar со всеми библиотеками внутри, и java -jar app.jar просто работает. Именно такой jar потом кладут в Docker-образ (апрель).

9. Maven и IntelliJ

IntelliJ понимает pom.xml и сама подставляет библиотеки, версию Java и папки исходников. Твой репозиторий открыт как обычный проект, поэтому ей надо подсказать:

  1. в дереве проекта правый клик по lesson0014/pom.xml → Add as Maven Project;
  2. справа появится панель Maven (буква m) — там фазы Lifecycle можно запускать двойным кликом;
  3. поменял pom.xml — нажми значок обновления (Reload All Maven Projects) или всплывающую кнопку Load Maven Changes, иначе IntelliJ будет подчёркивать красным новый import, хотя mvn в терминале соберёт.

Главное — терминал. Если mvn compile в терминале проходит, а IntelliJ подчёркивает — виновата IntelliJ (не обновилась). Наоборот не бывает: правда всегда в pom.xml и в mvn. Так работают и серверы сборки, у которых никакой IntelliJ нет.

10. target/ — не в Git

В target/ лежат .class и .jar — их всегда можно пересобрать из исходников. В Git кладут исходники, а не результат сборки: иначе каждая сборка давала бы «изменения» в git status. Допиши строку в .gitignore в корне репозитория:

target/

Без / в начале — значит «папка target на любом уровне», и в lesson0014/, и в будущих проектах. Проверка: после mvn package команда git status не должна показывать target/.

Частые вопросы

Почему проект в lesson0014/ в корне, а не в src/lesson0014/, как всегда?

У Maven-проекта своя папка src/ внутри. Положи его в src/lesson0014/ — получится src/lesson0014/src/main/java/..., и IntelliJ, у которой весь твой src/ отмечен как корень исходников, решит, что пакет называется lesson0014.src.main.java.ru..., и подчеркнёт всё красным. Поэтому Maven-проект — отдельная папка рядом с src/. Правило «весь код пишу сам» не меняется. Консольный банк в ноябре будет уже отдельным репозиторием.

Надо ли запоминать pom.xml наизусть?

Нет. Скелет (xmlns-строки) все копируют, координаты библиотек — с Maven Central. Знать нужно структуру: что такое GAV, где properties, где dependencies/dependency, где build/plugins/plugin, — чтобы читать чужой pom.xml и правильно вставить новый блок. Именно это и проверяют на собеседовании.

Чем Maven отличается от Gradle?

Задача одна, файл другой: у Gradle build.gradle — код на Groovy или Kotlin вместо XML. Координаты, Maven Central, структура src/main/java — те же. Spring Initializr предлагает оба; в банках и вакансиях Казани чаще встречается Maven. Выучив Maven, Gradle читаешь за вечер.

Что такое SNAPSHOT и когда его убирать?

«Версия в работе». Пока проект развивается, 1.0-SNAPSHOT. Когда выпускаешь — 1.0, и такая версия уже не должна меняться никогда (как запушенный коммит). Для учебных проектов SNAPSHOT можно не трогать.

mvn пишет BUILD SUCCESS, но печать моего main не видно.

Ты запустил mvn compile, а не mvn compile exec:java: компиляция не запускает программу. И проверь флаг -q — «тихий режим», он прячет строки [INFO], но вывод твоей программы оставляет.

Проверь себя

1. Ты запустил mvn package. Какие фазы выполнятся?

Вызванная фаза выполняет все предыдущие. Поэтому упавший тест не даст собрать jar. clean — отдельный цикл, сам не запускается.

2. Класс начинается с package ru.ilyagrg.bank;. Где должен лежать файл?

Корень пакетов — src/main/java, каждая точка в имени пакета — вложенная папка.

3. Сборка пишет Could not resolve dependencies ... commons-lang3:jar:3.99.0. В чём дело?

Ошибка Maven, до компиляции не дошло: координаты не находятся. Забытый import дал бы COMPILATION ERROR, незакрытый тег — Non-parseable POM, не та папка — No sources to compile.

4. mvn compile прошёл, а java -cp target/classes ...Main падает с NoClassDefFoundError: .../StringUtils. Почему?

Maven подставляет библиотеки в -cp сам, но только для своих команд. Руками запущенная java о них не знает. Отсюда mvn exec:java.

5. Нужна вторая библиотека. Куда вставить её <dependency>?

Коробка <dependencies> одна на файл, в ней сколько угодно <dependency>. Второй блок — Duplicated tag.
