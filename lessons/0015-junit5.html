JUnit 5: тесты вместо check()

После этого урока ты напишешь настоящие тесты: с assertEquals, assertThrows, @BeforeEach и параметрами. Их запускает одна команда mvn test, а упавший тест не даёт собрать проект.

Зачем этот урок для backend. На работе код без тестов обычно не пройдёт проверку перед слиянием. Spring Boot подключает JUnit по умолчанию, так что тесты твоего будущего REST API будут написаны почти тем же синтаксисом, что и сегодня. На собеседовании спросят, как ты тестируешь код и что такое граничный случай. Сегодня появится честный ответ.

1. Чем плох твой check()

Твой метод честно служил семь уроков. Но у него есть четыре дыры, и все ты уже видел:

Exception in thread "main"
Одно исключение убивает всё. Проверки после него не запускаются, и ты не узнаешь, сломаны ли они
ОШИБКА: ...
BUILD SUCCESS
Maven не знает о провале. Для него программа просто что-то напечатала. Он соберёт jar даже со строкой «ОШИБКА»
boolean thrown = false;
try { ... } catch ...
Много шума. Шесть строк на проверку одного исключения
check("...", a == b)
Нет деталей. Видно, что проверка не прошла, но не видно, что получилось и что ожидалось

JUnit — стандартная библиотека тестов для Java (JUnit 5 User Guide). Тест здесь — обычный метод с пометкой @Test. JUnit сам находит такие методы, запускает каждый отдельно и считает результат.

Как в Python. Это pytest. def test_total(): assert total() == 140 превращается в метод с @Test и assertEquals(140, total()). pytest.raises(ValueError) становится assertThrows(...), фикстура — @BeforeEach, а @pytest.mark.parametrize — @ParameterizedTest.

2. Подключаем JUnit — и обходим ловушку

Весь урок показан на соседнем примере: простой магазин Shop, в нём товары и цены. Банк останется тебе на домашку.

package ru.ilyagrg.shop;

public class Shop {
    private Map<String, Integer> prices = new HashMap<>();

    public void addProduct(String name, int price) {
        if (price < 0) {
            throw new IllegalArgumentException("Цена меньше нуля: " + price);
        }
        prices.put(name, price);
    }

    public Optional<Integer> findPrice(String name) {
        return Optional.ofNullable(prices.get(name));
    }

    public int total() {
        return prices.values().stream().mapToInt(Integer::intValue).sum();
    }

    public int count() {
        return prices.size();
    }
}

3. Первый тест — пишем с нуля

  1. Создай файл там, где его ищет Maven. Тот же пакет, что у проверяемого класса, но корень — src/test/java. Имя заканчивается на Test.

4. Проверки: какую когда

Все они — статические методы класса Assertions. Для каждой нужен свой import static.

ПроверкаКогда
assertEquals(140, shop.total())значение равно ожидаемому. Сравнивает через equals. Твой основной инструмент
assertTrue(list.isEmpty())условие истинно
assertFalse(repo.existsById(id))условие ложно
assertSame(account, found)это один и тот же объект, сравнение через == (урок 8)
assertThrows(...)код бросает исключение (раздел 5)

Как сравнивать разные типы

assertEquals(2, shop.count());                                 // числа
assertEquals("Цена меньше нуля: -1", e.getMessage());          // строки

assertEquals(Optional.of(90), shop.findPrice("молоко"));       // Optional со значением
assertTrue(shop.findPrice("сыр").isEmpty());                   // пустой Optional

assertEquals(List.of("Adam", "Ilya"), bank.richOwners(100));   // список: те же элементы в том же порядке
assertEquals(Map.of("Ilya", 300), bank.balanceByOwner());      // Map: те же пары

Точное значение лучше общего условия. Эта строка заменяет твои allMatch(...) && size() != 0:

assertEquals(List.of("Adam", "Ilya"), bank.richOwners(100));

Она проверяет сразу и состав, и порядок, и отсутствие дублей. На пустом результате она падает сама. Условие allMatch в тесты больше не бери.

Частые ошибки

Сравнил число с Optional. Написал assertEquals(90, shop.findPrice("молоко")). Компилятор не возражает, но тест падает:

expected: <90> but was: <Optional[90]>

Забыл import static. Это ошибка компиляции, и mvn покажет её до запуска тестов:

[ERROR] src/test/java/ru/ilyagrg/shop/ShopTest.java:[26,9] cannot find symbol
  symbol:   method assertEquals(int,int)
  location: class ru.ilyagrg.shop.ShopTest

Перепутал порядок. Сначала ожидаемое, потом полученное. assertEquals(shop.total(), 140) тоже работает, но при падении сообщение будет обманывать: expected покажет настоящий результат.

5. assertThrows: проверяем исключение

шаблон

assertThrows(КлассИсключения.class, () -> код, который должен упасть);

Так выглядит тот же смысл, что у твоих шести строк с try/catch:

было

boolean thrown = false;
try {
    shop.addProduct("сыр", -1);
} catch (IllegalArgumentException e) {
    thrown = true;
}
check("Цена меньше нуля", thrown);

стало

assertThrows(
    IllegalArgumentException.class,
    () -> shop.addProduct("сыр", -1));

Собираем по шагам

  1. Какое исключение ждём? Пишем имя класса и .class. Так мы передаём в метод сам тип.

    assertThrows(IllegalArgumentException.class, );

  2. Что должно упасть? Код нельзя вызвать сразу: исключение вылетит раньше, чем JUnit успеет его поймать. Поэтому заворачиваем вызов в лямбду без параметров, как в разминке. JUnit сам её запустит и перехватит исключение.

    assertThrows(IllegalArgumentException.class, () -> shop.addProduct("сыр", -1));

  3. Нужны детали? assertThrows возвращает пойманное исключение. Сохрани его в переменную и проверь сообщение или поля:

    IllegalArgumentException e = assertThrows(
        IllegalArgumentException.class,
        () -> shop.addProduct("сыр", -1));

assertEquals("Цена меньше нуля: -1", e.getMessage());

  4. Состояние не должно испортиться. После ошибки объект должен остаться прежним. Проверь и это:

    assertEquals(2, shop.count());     // сломанный товар не добавился

Как он падает

Я убрал проверку цены из Shop — исключения нет:

Expected java.lang.IllegalArgumentException to be thrown, but nothing was thrown.

Я заменил исключение на другой тип:

Unexpected exception type thrown, expected: <java.lang.IllegalArgumentException> but was: <java.lang.IllegalStateException>

В отличие от твоего catch, чужое исключение не останавливает программу, а просто роняет один этот тест и подробно о нём сообщает.

6. @BeforeEach: свежий объект для каждого теста

В каждом тесте повторяется создание магазина с товарами. Общую подготовку выносят в метод с @BeforeEach. JUnit вызывает его перед каждым тестом (User Guide: Test Classes and Methods).

  1. Переменная становится полем класса. Без значения: значение появится в следующем шаге.

    class ShopTest {
    private Shop shop;

  2. Метод подготовки (нужен import org.junit.jupiter.api.BeforeEach;). Обрати внимание: shop = ..., а не Shop shop = .... Иначе ты создашь локальную переменную, а поле останется null.

        @BeforeEach
    void setUp() {
        shop = new Shop();
        shop.addProduct("молоко", 90);
        shop.addProduct("хлеб", 50);
    }

  3. Тесты используют поле и становятся короче:

        @Test
    void totalSumsAllPrices() {
        assertEquals(140, shop.total());
    }

    @Test
    void findPriceReturnsEmptyForMissingProduct() {
        assertTrue(shop.findPrice("сыр").isEmpty());
    }

Почему не один объект на все тесты. Тесты должны быть независимы, а порядок их запуска не гарантирован. Если один тест удалит товар, другой не должен об этом узнать. @BeforeEach каждый раз даёт новый магазин. У твоего tests() всё было наоборот: deleteUser менял банк для всех следующих проверок.

Нужен особый объект? Создай его прямо в тесте: assertEquals(0, new Shop().total());

7. Параметризованные тесты: один код, много данных

Когда тесты отличаются только данными, код не копируют. Нужно сделать три вещи: заменить @Test на @ParameterizedTest, указать источник данных и добавить параметр в метод (User Guide: Parameterized Tests).

Один параметр — @ValueSource

шаблон

@ParameterizedTest
@ValueSource(ints / strings = {значение1, значение2, ...})
void имяТеста(тип имя) {
    проверка с этим параметром
}
@ParameterizedTest
@ValueSource(ints = {-1, -100, Integer.MIN_VALUE})
void addProductRejectsAnyNegativePrice(int price) {
    assertThrows(IllegalArgumentException.class, () -> shop.addProduct("сыр", price));
}

Метод запустится три раза, и каждый запуск считается отдельным тестом. ints = соответствует параметру int, strings = — параметру String.

В @ValueSource нельзя указать null. Для него есть отдельная аннотация, которую можно поставить рядом:

@ParameterizedTest
@NullSource
@ValueSource(strings = {"", "   ", "Hello"})
void имяТеста(String value) { ... }      // 4 запуска: null, "", "   ", "Hello"

Несколько параметров — @CsvSource

шаблон

@ParameterizedTest
@CsvSource({
        "вход1, ожидаемое1",
        "вход2, ожидаемое2"
})
void имяТеста(Тип вход, Тип ожидаемое) { ... }
@ParameterizedTest
@CsvSource({
        "молоко, 90",
        "хлеб, 50"
})
void findPriceKnowsEachProduct(String name, int price) {
    assertEquals(Optional.of(price), shop.findPrice(name));
}

Каждая строка — один запуск, значения разделены запятой. JUnit сам преобразует текст в тип параметра: в int и даже в enum, если написать имя константы.

Импорты: org.junit.jupiter.params.ParameterizedTest и org.junit.jupiter.params.provider.ValueSource (там же NullSource и CsvSource).

8. Что именно тестировать: четыре вопроса

Самая частая твоя проблема — не синтаксис. Уроки 11–13 показали, что теряются проверки случая, когда «ничего нет». Задавай к каждому публичному методу четыре вопроса:

1. Обычный случай
Работает ли метод на типичных данных? Ожидаемое посчитано заранее: total() = 140
2. Пусто или нет
Что вернёт, когда ничего нет? Пустой магазин: total() = 0. Не нашёл: isEmpty()
3. Граница
Значение ровно на краю условия. Снять ровно весь баланс, цена ровно 0, порог ровно равен балансу
4. Ошибка
Плохие данные дают правильное исключение. А состояние после этого не меняется

Результат эксперимента: почему нужен и случай «нашёл»

Домашних экспериментов нет: я запустил их сам. В Shop я сломал метод так, чтобы он всегда возвращал пустоту: return Optional.empty();

Опыт 1. Я оставил в тестах только проверку isEmpty() для отсутствующего товара:

[INFO] Tests run: 7, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS

Метод полностью сломан — а сборка зелёная.

Опыт 2. Я вернул тесты случая «нашёл»:

[ERROR]   ShopTest.findPriceReturnsPriceOfExistingProduct:37 expected: <Optional[90]> but was: <Optional.empty>
[ERROR] Tests run: 10, Failures: 3, Errors: 0, Skipped: 0

Вывод: нужны обе стороны. Тест «нашёл» ловит метод, который всегда возвращает пустоту, а тест «не нашёл» ловит метод, который возвращает что попало. Ни один из них не заменяет другой.

Весь тестовый класс целиком

package ru.ilyagrg.shop;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
import org.junit.jupiter.params.provider.ValueSource;

import java.util.Optional;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.junit.jupiter.api.Assertions.assertTrue;

class ShopTest {
    private Shop shop;

    @BeforeEach
    void setUp() {
        shop = new Shop();
        shop.addProduct("молоко", 90);
        shop.addProduct("хлеб", 50);
    }

    @Test
    void totalSumsAllPrices() {
        assertEquals(140, shop.total());
    }

    @Test
    void totalOfEmptyShopIsZero() {
        assertEquals(0, new Shop().total());
    }

    @Test
    void findPriceReturnsPriceOfExistingProduct() {
        assertEquals(Optional.of(90), shop.findPrice("молоко"));
    }

    @Test
    void findPriceReturnsEmptyForMissingProduct() {
        assertTrue(shop.findPrice("сыр").isEmpty());
    }

    @Test
    void addProductRejectsNegativePrice() {
        IllegalArgumentException e = assertThrows(
                IllegalArgumentException.class,
                () -> shop.addProduct("сыр", -1));

        assertEquals("Цена меньше нуля: -1", e.getMessage());
        assertEquals(2, shop.count());
    }

    @ParameterizedTest
    @ValueSource(ints = {-1, -100, Integer.MIN_VALUE})
    void addProductRejectsAnyNegativePrice(int price) {
        assertThrows(IllegalArgumentException.class, () -> shop.addProduct("сыр", price));
    }

    @ParameterizedTest
    @CsvSource({
            "молоко, 90",
            "хлеб, 50"
    })
    void findPriceKnowsEachProduct(String name, int price) {
        assertEquals(Optional.of(price), shop.findPrice(name));
    }
}

Частые вопросы

Почему JUnit 5.11.4, если на Maven Central есть версии новее?

Новые версии есть, включая JUnit 6. Для учёбы нужен JUnit 5: на нём написано большинство существующих проектов и документации, а синтаксис из этого урока в новых версиях остаётся таким же. На этой версии я проверил все примеры. Сейчас возьми её, чтобы вывод совпадал.

Надо ли тестировать геттеры?

Простые — нет. Они проверяются сами в других тестах: assertEquals(100, account.getBalance()). Тестируй то, где есть логика и где можно ошибиться.

Можно ли несколько assert в одном тесте?

Да, если они проверяют одно поведение, как в addProductRejectsNegativePrice: тип, сообщение и неизменность магазина. Если получилось два разных поведения, раздели на два теста, тогда имя теста сразу скажет, что сломалось. Первая упавшая проверка завершает тест, следующие в нём не выполняются.

Как тестировать private-метод?

Никак напрямую, и это нормально. Он работает внутри публичных методов, поэтому проверяется через них: checkNumber проверяется вызовом openAccount(null, ...).

Зачем писать тест, если метод уже работает?

Чтобы он продолжал работать. Ты уже сам видел, как при переписывании на стримы и на Optional незаметно ломалось то, что раньше работало. Тест заметит это в следующий раз, когда ты поменяешь код.

Проверь себя

1. mvn test вывел Tests run: 0 и BUILD SUCCESS, а тесты в проекте есть. Что проверить в первую очередь?

Старый surefire:2.17 не видит тесты JUnit 5, а имя без Test не подходит под шаблон запуска. Оба случая дают зелёную сборку без тестов.

2. Почему в assertThrows вызов метода заворачивают в лямбду?

Аргументы вычисляются до вызова метода. Лямбда откладывает выполнение: assertThrows сам запускает её внутри своего try.

3. Как часто выполняется метод с @BeforeEach?

Поэтому каждый тест получает новый объект и не зависит от остальных.

4. Как лучше проверить richOwners, чтобы тест ловил и пустой результат, и дубли, и порядок?

Точный список проверяет состав, порядок и количество. На пустом результате allMatch вернёт true.

5. Что значит <scope>test</scope>?

Импорт JUnit в src/main/java даст package ... does not exist.

Домашка

В ветке feature/junit. Один шаг — один коммит. Правила для всех тестов:

  • Ожидаемое считай заранее и пиши точно. Без allMatch и без size() != 0.
  • Для каждого публичного метода задай четыре вопроса из раздела 8. Если вопрос неприменим — пропускай.
  • После каждого шага смотри на число в Tests run: оно должно вырасти.

Шаг 1. Проект и pom.xml

  1. Закоммить в main мои файлы (README, GLOSSARY, learning-records, уроки, справочник, RESOURCES), потом git push.
  2. git switch -c feature/junit.
  3. Скопируй проект без результатов сборки: cp -r lesson0014 lesson0015 && rm -rf lesson0015/target. Пакет оставь прежним, ru.ilyagrg.bank.
  4. В lesson0015/pom.xml добавь зависимость и плагин из раздела 2.
  5. Добавь lesson0015/pom.xml в IntelliJ через Add as Maven Project.
  6. cd lesson0015 && mvn test: BUILD SUCCESS, тестов пока нет. В выводе должен быть surefire:3.5.2, а не 2.17.

Шаг 2. AccountNumberTest — первый класс

  • Правильный номер: value() возвращает его.
  • Два одинаковых номера равны по equals и имеют одинаковый hashCode. Разные номера не равны.
  • Параметризованный тест: null, "", " ", номер без BANK бросают IllegalArgumentException. Используй @NullSource и @ValueSource.

Шаг 3. CurrencyTest

  • @CsvSource: каждая валюта и её символ. Для названий — отдельный такой же тест.
  • Валют ровно три; valueOf("USD") — это Currency.USD; valueOf("JPY") бросает исключение.

Шаг 4. BankAccountTest и SavingsAccountTest

Используй @BeforeEach. Обязательные случаи:

  • Конструктор: плохой владелец и отрицательный баланс.
  • deposit, withdraw: обычный случай и отрицательная сумма.
  • Граница: снять ровно весь баланс — на счёте 0.
  • Снять больше баланса: InsufficientFundsException, в нём верный getAvailable(), баланс не изменился.
  • transferTo: оба баланса после перевода. При нехватке денег оба баланса прежние. Перевод самому себе и на null.
  • SavingsAccount: снять ровно лимит можно, на единицу больше — исключение. addInterest: точная сумма.

Шаг 5. InMemoryRepositoryTest — случаи «есть» и «нет»

Это те проверки, которые мы отложили в уроках 13–14. Теперь каждая получает отдельный тест:

  • findById: нашёл, и значение верное. Не нашёл — isEmpty().
  • existsById: есть и нет.
  • count и findAll: пустой репозиторий и заполненный.
  • deleteById: удалил — больше не находится. Удаление отсутствующего — исключение.
  • save с null — исключение.
  • findById(null) должен бросать IllegalArgumentException. Этот тест у тебя упадёт: при сокращении метода ты потерял проверку. Увидь его красным, затем исправь метод, не меняя тест. Это твоя первая ошибка, найденная тестом.

Шаг 6. BankTest — главный

Перенеси и дополни все проверки банка из Main. Для @BeforeEach возьми банк с тремя счетами, где у одного владельца два счёта, а балансы удобно считать в уме.

  • openAccount: null в каждом параметре, занятый номер. findAccount: другой объект с тем же номером находит тот же счёт (assertSame); нет счёта — исключение.
  • transfer: балансы после перевода; нет получателя — AccountNotFoundException, баланс отправителя прежний.
  • totalBalance, owners, balanceByOwner, accountsByOwner: заполненный и пустой банк.
  • sortedByOwner, sortedByBalanceDesc: точный порядок.
  • findAccounts, countAccounts: есть подходящие и нет ни одного.
  • richOwners: точный список. Один порог ровно равен балансу (граница), у владельца с двумя счетами подходят оба (дубли). Порог, под который никто не подходит.
  • findRichest: какой именно счёт; пустой банк. deleteUser: удаляет; отсутствующий номер.

Шаг 7. Чистка и сборка

  1. Добавь короткий CollectionUtilsTest: max для чисел и строк, пустой список.
  2. Из Main удали check() и все проверки. Оставь короткий пример работы банка: открыть два счёта, сделать перевод, напечатать балансы.
  3. mvn clean package: BUILD SUCCESS, jar собран.
  4. Слей в main, удали ветку, git push.
