equals и hashCode: когда два объекта «одинаковые»

После этого урока ты сможешь объяснить разницу между == и equals, правильно переопределить equals и hashCode у своего класса и решить, нужно ли это делать вообще. Это один из самых частых вопросов на собеседованиях junior Java.

Откуда урок. Он собран из твоих же вопросов: other.owner == owner в уроке 3, «2 и 1» в HashSet в уроке 7 и загадка с Integer. Сегодня все три получат одно объяснение.

Разминка

1. Обещанный повтор (урок 6): почему реализация интерфейса не может сделать метод закрытее, чем в интерфейсе?

Код, который держит переменную типа интерфейса (Notifier notifier), вызывает notifier.send(...) — компилятор разрешает это, потому что в интерфейсе метод public. Какой объект там окажется, компилятор не знает. Если бы реализация могла спрятать send, обещание договора «этот метод можно вызвать» было бы нарушено. Поэтому сужать доступ запрещено.

2. Что напечатал твой код в уроке 7 и как ты это объяснил? 
Set<BankAccount> set = ...; set.add(new BankAccount("Илья", 100)); set.add(new BankAccount("Илья", 100));
// 2
Set<String> names = ...; names.add(new String("Илья")); names.add(new String("Илья"));
// 1

Твоя догадка: «воспринимает объекты как разные, несмотря на одинаковые поля». Верно. Сегодня узнаем, как именно HashSet решает, разные они или нет, и почему строки он считает одинаковыми.

3. Что сравнивает ==, если слева и справа объекты?

Ссылки: указывают ли две переменные на один и тот же объект. Ты использовал это правильно в transferTo: other == this — «это тот же самый счёт?»

1. Два вопроса про «одинаковость»

У слова «одинаковые» два разных смысла, и в Java для них два разных инструмента:

ВопросJavaPythonПример
Это тот же самый объект?a == ba is bтот же счёт, не копия
Эти объекты равны по смыслу?a.equals(b)a == bдве купюры по 100 рублей

Осторожно: == в Python и == в Java для объектов означают разное. Питоновскому == соответствует equals, а джавовскому == — питоновский is.

Аналогия: у тебя и у друга по купюре в 100 рублей. Это разные бумажки (== — false), но для оплаты они равноценны (equals — true). А вот если ты передал другу свою купюру — это та же самая бумажка (== — true).

Как это выглядит в коде

Возьмём класс «деньги» — сумма и валюта. Пока без equals:

public class Money {
    private int amount;
    private String currency;

    public Money(int amount, String currency) {
        this.amount = amount;
        this.currency = currency;
    }
}

Money a = new Money(100, "RUB");
Money b = new Money(100, "RUB");
Money c = a;

a == b        // false — два разных объекта (два new)
a == c        // true  — c ссылается на тот же объект, что a
a.equals(b)   // false (!) — хотя поля одинаковые

Почему equals вернул false? Помнишь из урока 5: если класс ничего не наследует явно, его родитель — Object. Наш Money получил от Object метод equals, а тот устроен очень просто — по документации он сравнивает через ==. Java не знает, что для денег важны сумма и валюта. Это знаешь только ты, значит, equals нужно переопределить.

А String равенство по содержимому уже умеет — разработчики Java переопределили в нём equals. Поэтому names в уроке 7 дал 1. Я проверил: "Илья" == new String("Илья") — false, а "Илья".equals(new String("Илья")) — true.

Проверь себя: в уроке 3 у тебя было other.owner == owner. Почему с литералами это работало, а с new String("Илья") — нет?

== сравнивает ссылки. Одинаковые строковые литералы Java хранит в одном экземпляре (я проверил: "Илья" == "Илья" — true), поэтому ссылки совпадали случайно. new String создаёт новый объект — ссылка другая. Строки по содержимому всегда сравнивают через equals.

2. Переопределяем equals

Вот equals для Money. Это стандартный шаблон, который ты будешь писать (или генерировать в IntelliJ) много раз:

@Override
public boolean equals(Object o) {
    if (this == o) {
        return true;
    }
    if (o == null || getClass() != o.getClass()) {
        return false;
    }
    Money other = (Money) o;
    return amount == other.amount && currency.equals(other.currency);
}
@Override public boolean equals(Object o)
Сигнатура как у Object.equals: параметр — Object, не Money. Иначе это будет перегрузка, а не переопределение (раздел 4). @Override проверит.
if (this == o) { return true; }
Сравниваем объект сам с собой — точно равны. Быстрый выход.
if (o == null || getClass() != o.getClass()) { return false; }
null ни чему не равен. getClass() — «точный класс объекта». Деньги не могут быть равны строке или счёту, даже если там тоже есть число 100. Порядок важен: сначала null, иначе o.getClass() упадёт с NullPointerException (тот же шаблон, что «сначала null, потом isBlank»).
Money other = (Money) o;
Приведение типа (cast). Переменная o — типа Object, и по правилу 1 из урока 5 у неё нельзя спросить amount. Мы только что проверили, что объект на самом деле Money, поэтому говорим компилятору: «считай его Money». Объект не меняется — меняется только тип переменной, через которую мы на него смотрим.
return amount == other.amount && currency.equals(other.currency);
Сравнение по смыслу. amount — int, примитив, для него == правильно. currency — String, объект, для него equals. Правило: примитивы через ==, объекты через equals. А other.amount можно читать, хотя поле private: мы внутри класса Money (урок 3).

Проверено на JDK 21 с этим equals:

a.equals(b)                      // true  — сумма и валюта совпали
a.equals(new Money(100, "USD"))  // false — валюта другая
a.equals(null)                   // false — без исключения
a.equals("100 RUB")              // false — другой класс
a == b                           // false — по-прежнему два разных объекта

Обрати внимание на последнюю строку: equals ничего не меняет в ==. Это два разных вопроса, и оба нужны.

Правила, которые должен соблюдать equals

Документация Object.equals требует, чтобы равенство вело себя «разумно». Если ты пишешь по шаблону выше, правила выполняются сами, но знать их стоит — спрашивают на собеседованиях:

  • Рефлексивность: a.equals(a) — всегда true.
  • Симметричность: если a.equals(b), то и b.equals(a).
  • Транзитивность: если a равно b, а b равно c, то a равно c.
  • Постоянство: пока объекты не менялись, ответ не меняется.
  • a.equals(null) — всегда false, без исключения.
Проверь себя: что будет, если в equals написать currency == other.currency?

Сравнятся ссылки на строки. С литералами "RUB" это случайно сработает (они в одном экземпляре), а со строкой, пришедшей, например, из формы или из базы данных, — нет. Та же ошибка, что в уроке 3. Объекты — через equals.

3. hashCode: как HashSet ищет

Переопределили equals — готово? Проверим. Класс с правильным equals, но без hashCode:

Set<EqOnly> set = new HashSet<>();
set.add(new EqOnly(100, "RUB"));
set.add(new EqOnly(100, "RUB"));
e1.equals(e2)     // true
set.size()        // 2 (!)

Я проверил: equals говорит «равны», а HashSet всё равно хранит два. Почему — нужно понять, как он устроен.

Как устроен HashSet (и HashMap)

Помнишь гардероб из урока 7? Представь, что крючков тысяча и они разбиты на ряды. Гардеробщик не обходит все тысячу крючков: по номерку он сразу понимает ряд, и сравнивает только в нём.

HashSet делает так же, в два шага:

  1. Выбрать «ряд». Вызвать у объекта hashCode() — метод, который возвращает число (int). По этому числу выбирается «корзина» (bucket). Смотреть будем только в ней.
  2. Сравнить внутри ряда. С каждым объектом в этой корзине вызвать equals. Нашёлся равный — значит, такой элемент уже есть.

Теперь ясно, что пошло не так. hashCode мы не переопределили, значит, работает версия из Object: она даёт разные числа для разных объектов (в документации — «as far as is reasonably practical»). Два наших объекта попали в разные корзины. До шага 2 дело не дошло: в корзине второго объекта первого нет, сравнивать не с кем. equals так и не был вызван.

Интересная деталь: list.contains(e2) для этого же класса вернул true (проверено). ArrayList не использует хеши, он вызывает equals у каждого элемента подряд. Поэтому без hashCode «ломаются» только HashSet и HashMap — и это особенно коварно.

Договор hashCode

Если два объекта равны по equals, их hashCode обязаны совпадать.

Обратное не требуется: разные объекты могут случайно получить одинаковый hashCode (это называется коллизия). Тогда они попадут в одну корзину, и equals на шаге 2 их различит. Коллизии лишь чуть замедляют поиск, а нарушение главного правила ломает HashSet.

Object.hashCode (Java 21): «If two objects are equal according to the equals method, then calling the hashCode method on each of the two objects must produce the same integer result.»

Как написать hashCode

import java.util.Objects;

@Override
public int hashCode() {
    return Objects.hash(amount, currency);
}

Objects.hash(...) — готовый метод: перемешивает значения полей в одно число. Правило выбора полей простое: те же поля, что сравниваются в equals. Тогда равные объекты гарантированно дадут равные числа. У двух наших Money(100, "RUB") оба hashCode — 85564 (проверено).

Теперь всё работает:

Set<Money> s = new HashSet<>();
s.add(new Money(100, "RUB"));
s.add(new Money(100, "RUB"));
s.size()                              // 1
s.contains(new Money(100, "RUB"))     // true — совсем новый объект, а находится

Map<Money, String> m = new HashMap<>();
m.put(a, "x");
m.get(new Money(100, "RUB"))          // "x" — ключ найден по равному объекту

Главное правило урока: equals и hashCode переопределяют всегда вместе. Только один из них — ошибка.

Проверь себя: hashCode всегда возвращает 42 для любого объекта. Договор нарушен? Будет ли работать HashSet?

Договор не нарушен: равные объекты дают равные числа (все дают 42). HashSet будет работать правильно, но все объекты окажутся в одной корзине, и поиск превратится в перебор, как у списка. Корректно, но медленно.

4. Ловушка: equals(Money other) вместо equals(Object o)

Очень частая ошибка — написать параметр «правильного» типа:

public boolean equals(Money other) {      // ← Money, не Object
    return other != null && amount == other.amount;
}

Это не переопределение, а перегрузка (урок 1): другой тип параметра — другая сигнатура. Теперь у класса два метода equals: твой, с Money, и унаследованный от Object, с Object. Я проверил на классе с такой ошибкой:

o1.equals(o2)              // true  — вызвана твоя перегрузка (o2 типа Overload)
Object oo = o2;
o1.equals(oo)              // false — вызвана версия Object, по ссылкам
set.size()                 // 2     — HashSet вызывает equals(Object)

HashSet и HashMap написаны задолго до твоего класса и вызывают equals(Object). Твою перегрузку они не видят. Спасает то же, что в уроке 5: @Override. С ним такая ошибка не скомпилируется: method does not override or implement a method from a supertype.

5. Ловушка: изменяемые поля в hashCode

Представь, что ты сделал equals и hashCode у счёта по владельцу и балансу. Проверим (класс Mut — упрощённый счёт с такими методами):

Mut acc = new Mut("Илья", 100);
Set<Mut> set = new HashSet<>();
set.add(acc);
acc.deposit(50);                // баланс изменился → hashCode изменился
set.contains(acc)               // false (!) — тот же самый объект не находится
set.size()                      // 1 — но он там лежит

Трассировка: при add объект положили в корзину, вычисленную по балансу 100. После deposit hashCode считается по балансу 150 — contains идёт в другую корзину и там ничего не находит. Объект «потерялся» внутри набора. Вывод: поля, которые меняются, не должны участвовать в equals и hashCode объектов, которые лежат в HashSet или служат ключами HashMap.

6. Главный вопрос: а нужно ли вообще?

Не каждому классу нужен equals по полям. Есть два вида объектов:

Объект-значение (value object)Сущность (entity)
Что важнотолько значение«кто это», его личность
ПримерыMoney, String, Integer, номер счёта, датабанковский счёт, клиент, заказ
Тестдве купюры по 100 ₽ взаимозаменяемыдва счёта Ильи по 100 ₽ — разные счета
equalsпо всем полямне переопределять (по ссылке) или по уникальному номеру

Посмотри на свой BankAccount. У Ильи могут быть два счёта по 100 рублей — карта и накопительный. Если сделать equals по владельцу и балансу, банк будет считать их одним счётом, а HashSet выкинет один из них. Плюс баланс меняется (раздел 5). Так что результат «2» из урока 7 для счетов — правильный. Именно так и должно быть.

А вот номер счёта — это значение: строка "40817-001", пришедшая из формы, и та же строка, сохранённая в банке, обозначают один и тот же счёт. Поэтому ключом Map у тебя служит строка, у которой equals по содержимому. В домашке ты сделаешь свой класс номера счёта.

В Spring и базах данных это различие встретится снова: сущности там обычно сравнивают по уникальному идентификатору (id).

7. Загадка с Integer

В уроке 7 я показал: два одинаковых Integer из Map через == — то true, то false. Теперь ты можешь объяснить это сам. Проверено на JDK 21:

Integer i1 = 127, i2 = 127;
Integer i3 = 128, i4 = 128;
i1 == i2        // true
i3 == i4        // false
i3.equals(i4)   // true

Integer — объект, и == сравнивает ссылки. Но Java заранее создаёт и переиспользует объекты для маленьких чисел: документация гарантирует кеш «in the range -128 to 127». Для 127 обе переменные получают один и тот же готовый объект — ссылки равны. Для 128 создаются два разных объекта — ссылки разные.

Вывод тот же, что для строк: объекты, в том числе Integer, сравнивают через equals. Твоя проверка в уроке 7 (Integer == int) была корректна только потому, что справа был примитив int, и Java распаковала Integer в число.

8. Частые вопросы

IntelliJ может сгенерировать equals и hashCode?

Да: Alt+Insert → equals() and hashCode(), выбираешь поля. В реальной работе так и делают. В домашке напиши руками один раз, чтобы понимать каждую строку сгенерированного кода — на собеседовании попросят написать на листе.

Я видел if (!(o instanceof Money other)) return false;. Это то же самое?

Почти. instanceof проверяет «является ли объект Money или его потомком», а с Java 16 он ещё и сразу заводит переменную other — без отдельного приведения. Разница с getClass() — в потомках: getClass() требует точного совпадения класса. Для начала используй вариант с getClass(), как IntelliJ генерирует по умолчанию.

А если поле может быть null?

currency.equals(other.currency) упадёт, если currency — null. Безопасный вариант — Objects.equals(currency, other.currency): он сам обрабатывает null (проверено: Objects.equals(null, null) — true, Objects.equals("a", null) — false). Лучше же — не допускать null в поле проверкой в конструкторе, как ты уже умеешь.

Есть способ не писать всё это руками?

Да — record (Java 16+): специальный вид класса для объектов-значений, у которого equals, hashCode и toString по всем полям создаются автоматически. Это урок 13. Сегодня важно понять, что именно он генерирует.

Зачем hashCode, если можно сравнить всё через equals?

Скорость. equals со всеми элементами — это перебор, как у List. hashCode за один шаг сужает поиск до одной маленькой корзины. На миллионе элементов это разница между «мгновенно» и «секунды».

9. Проверь себя

Без подглядывания. Ошибся — вернись к разделу.

1. У Money правильно переопределены equals и hashCode. Чему равно new Money(100, "RUB") == new Money(100, "RUB")?

== на объектах всегда сравнивает ссылки. Два new — два объекта. equals на == не влияет.

2. В классе переопределён только equals, без hashCode. В HashSet добавили два равных объекта. Сколько элементов?

Без своего hashCode объекты получают разные числа и попадают в разные корзины. equals даже не вызывается. Компилятор об этом не предупредит.

3. В классе написан public boolean equals(Money other) без @Override. Что это?

Тип параметра другой — значит, сигнатура другая, это новый метод. Коллекции вызывают equals(Object), и работает версия Object по ссылкам. @Override поймал бы ошибку.

4. Что требует договор hashCode?

Обязательно только одно направление: равные объекты дают равные числа. Совпадение чисел у разных объектов (коллизия) допустимо.

5. Integer x = 1000, y = 1000; Чему равно x == y?

Integer — объект, == сравнивает ссылки. Кеш гарантирован только для -128…127, а 1000 — два разных объекта. Сравнивай через equals.

System.out.println(c == d);
System.out.println(c.equals(d));
System.out.println(s1 == s2);
System.out.println(s1 == s3);
System.out.println(s1.equals(s3));
