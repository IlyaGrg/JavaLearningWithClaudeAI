1. Проблема: любой может испортить твой объект

Вот Product из урока 2. Поля у него открыты: в объявлении нет модификатора доступа, и любой класс в пакете может делать с ними что угодно.

Product tea = new Product("Чай", 250, 10);

tea.price = -1000;      // отрицательная цена
tea.quantity = -5;      // минус пять пачек на складе
tea.name = null;        // товар без названия

Компилятор всё это пропустит: -1000 — корректный int, а null — корректное значение для String. Компилятор проверяет типы, а не смысл.

Теперь проследим, что будет дальше, шаг за шагом:

  1. Где-то в коде (чужом, твоём, написанном полгода назад) случайно выполнилось tea.price = -1000.
  2. Программа не упала. Объект живёт дальше с отрицательной ценой.
  3. Через час вызывается cartTotal(cart) и выдаёт сумму меньше, чем должна быть.
  4. Клиент оплачивает заниженную сумму. Ошибку замечают через неделю по отчётам.
  5. Ты ищешь, какая из сотен строк во всём проекте записала -1000. Поле открыто, значит, виновником может быть любая.

Самое неприятное здесь: ошибка проявляется далеко от места, где её совершили. Это самый дорогой вид бага.

Банковская версия. Вместо товара представь банковский счёт:

account.balance = 1_000_000;    // и всё, у клиента миллион

Если поле balance можно менять откуда угодно, никакая проверка «хватает ли денег на списание» не спасёт: её можно просто обойти. Поэтому в банковском коде ни одно поле не бывает открытым. Это не вопрос вкуса, это требование безопасности.

Идея инкапсуляции в одном предложении

Объект сам отвечает за свои данные: поля спрятаны, а снаружи доступны только методы, и каждый метод проверяет, что после него объект останется в правильном состоянии.

Аналогия — банкомат. Внутри лежат деньги (поля), но открыть сейф и взять пачку нельзя. Есть только кнопки (методы): «снять», «внести», «показать баланс». Кнопка «снять» сначала проверит ПИН и остаток, и только потом выдаст деньги. Сейф защищён от тебя, а ты защищён от ошибок сейфа.

Проверь себя: почему компилятор не запрещает tea.price = -1000?

Компилятор проверяет только типы: -1000 — это int, поле тоже int, всё совпадает. О том, что цена не может быть отрицательной, знаешь только ты. Значит, это правило должен выразить в коде ты, внутри класса.

2. Модификаторы доступа: кто что видит

Модификатор доступа — слово перед полем, методом, конструктором или классом. Оно говорит компилятору, из каких мест кода к этому члену класса можно обращаться. Ты уже видел public и писал поля вообще без модификатора. Всего вариантов четыре:

МодификаторСвой классСвой пакетНаследникиВсе остальные
privateданетнетнет
(ничего не написано)даданетнет
protectedдададанет
publicдададада

Источник: Oracle — Controlling Access to Members of a Class.

Как читать таблицу, на примере поля price класса Product:

  • private int price; — к полю можно обратиться только из кода, написанного внутри класса Product. Из Shop, Main и любого другого класса нельзя, даже если он в том же пакете.
  • int price; (без модификатора, так было у тебя) — можно из любого класса в том же пакете lesson0002. Поэтому Shop мог писать product.price.
  • protected — понадобится в уроке про наследование. Пока пропускаем.
  • public — можно откуда угодно, из любого пакета.

Что происходит, если нарушить private

Это ошибка компиляции, а не запуска. Программа даже не соберётся:

// в классе Main, а поля Product объявлены как private:
tea.price = -1000;
// error: price has private access in Product
System.out.println(tea.name);
// error: name has private access in Product

Обрати внимание: запрещено и читать (tea.name), и писать (tea.price = ...). private закрывает поле полностью.

Это и есть защита. Ошибка ловится в IntelliJ ещё до запуска, а не через неделю по отчётам.

Главное правило

Официальный туториал Oracle формулирует его так: «Use private unless you have a good reason not to» — используй private, если нет веской причины сделать иначе. И отдельно: «Avoid public fields except for constants» — не делай поля публичными, кроме констант.

На практике:

  • поля — всегда private;
  • методы и конструкторы, которыми должны пользоваться другие классы, — public;
  • вспомогательные методы, нужные только самому классу, — private.
Проверь себя: поле private int price в классе Product. Можно ли написать price = 5 внутри метода класса Product? А внутри Shop, если он в том же пакете?

Внутри Product — да: private означает «видно в своём классе». Внутри Shop — нет, даже в том же пакете: пакет открывает доступ только для полей без модификатора.

3. Геттеры: разрешаем читать

Мы закрыли поля, и теперь Shop не может даже узнать цену товара. Читать данные нужно, поэтому даём к ним доступ через метод.

Геттер (от англ. get — получить) — public-метод, который просто возвращает значение поля:

public int getPrice() {
    return price;
}

Снаружи вместо tea.price теперь пишут tea.getPrice().

Соглашение об именах

Имена геттеров в Java строго договорные, и на них полагаются библиотеки, включая Spring:

  • поле price → геттер getPrice(): get + имя поля с большой буквы;
  • поле name → getName();
  • для boolean-поля принято is: поле active → isActive().

Это соглашение называется JavaBeans. Через полгода Spring будет превращать твои объекты в JSON для REST-ответов, находя данные именно по геттерам. Нет геттера getPrice() — не будет поля "price" в JSON.

«Но это же то же самое, что открытое поле?»

Хороший вопрос, его задают все. Нет, не то же самое, и вот почему:

  1. Только чтение. Геттер позволяет прочитать цену, но не изменить её. С открытым полем можно и то и другое.
  2. Свобода менять внутренности. Допустим, через год ты решишь хранить цену в копейках (long priceKopecks), а не в рублях. Если все пользовались getPrice(), ты меняешь только тело геттера: return (int) (priceKopecks / 100);. Остальные сотни мест в коде ничего не заметят. С открытым полем пришлось бы переписать каждое место, где упоминается .price.

4. Сеттеры с проверкой: разрешаем менять, но правильно

Иногда поле действительно нужно менять снаружи: цену товара меняют, это нормально. Для этого есть сеттер (от set — установить). Если сеттер просто присваивает значение, он не лучше открытого поля. Весь смысл сеттера в том, что он сначала проверяет значение:

public void setPrice(int price) {
public — вызывать можно откуда угодно. void — ничего не возвращает: его работа — изменить объект. Имя: set + имя поля.
if (price < 0) {
Здесь price — это параметр: новое значение, которое нам предлагают. Оно ещё не записано в объект. Мы проверяем его до записи.
throw new IllegalArgumentException(
Бросаем исключение — аварийно прерываем метод. Подробно разберём в разделе 5.
"Цена не может быть отрицательной: " + price);
Сообщение об ошибке. Пиши его так, чтобы по нему было понятно, что не так и какое значение пришло. Через месяц это сэкономит тебе час отладки.

Сюда мы попадаем, только если проверка прошла. this.price — поле объекта, price — параметр, как в конструкторе из урока 2.

Обрати внимание на порядок: сначала проверка, потом запись. Если бы мы сначала записали, а потом проверили, объект уже успел бы испортиться.

Нужен ли сеттер каждому полю?

Нет. Это частая ошибка новичков: IntelliJ умеет одной командой сгенерировать геттер и сеттер для всех полей, и люди так и делают. Для каждого поля спроси себя: должно ли оно меняться после создания объекта?

  • Название товара после создания обычно не меняется → геттер есть, сеттера нет. Значение задаётся один раз в конструкторе.
  • Цена меняется → сеттер с проверкой.
  • Баланс счёта меняется, но не произвольно. Об этом подробнее в разделе 7.
Проверь себя: что не так с этим сеттером?

        throw new IllegalArgumentException("Цена отрицательная");
    }

Неправильный порядок: отрицательная цена уже записана в поле, а исключение бросается после этого. Объект испорчен. Сначала проверка, потом присваивание.

5. Исключение: как сказать «так нельзя»

Что должен сделать сеттер, если ему передали -1000? Есть несколько вариантов, и только один из них правильный:

  • Молча проигнорировать. Плохо: вызывающий код уверен, что цена изменилась, а она не изменилась. Ошибка опять всплывёт далеко от места, где её совершили.
  • Напечатать «ошибка» в консоль. Плохо: в backend консоль никто не читает, а программа идёт дальше с неверными данными. И помни раздел из ревью урока 2: метод не знает, где его вызвали.
  • Остановить выполнение и громко сообщить, что именно не так. Это и есть исключение.

Ты уже видел исключения

NullPointerException и IndexOutOfBoundsException из прошлых домашек — это исключения, которые бросила сама Java, когда ты сделал что-то невозможное. Теперь ты будешь бросать их сам, когда кто-то пытается сделать что-то запрещённое правилами твоего класса.

Разбор строки throw по словам

throw new IllegalArgumentException("Цена не может быть отрицательной: " + price);
  • new IllegalArgumentException(...) — создаём объект-исключение. Это обычный объект, такой же new, как new Product(...). В конструктор передаём текст ошибки. IllegalArgumentException — это готовый класс из Java, название значит «недопустимый аргумент». Он предназначен ровно для нашего случая: метод вызвали с неправильным значением параметра. Документация IllegalArgumentException
  • throw — «бросить». Метод немедленно прекращает работу, как при return, но вместо значения наружу летит исключение. Строки после throw не выполняются.

Что происходит при запуске: по шагам

public static void main(String[] args) {
    Product tea = new Product("Чай", 250);
    System.out.println(tea.getName() + ": " + tea.getPrice());

    tea.setPrice(300);
    System.out.println(tea.getName() + ": " + tea.getPrice());

    tea.setPrice(-1000);
    System.out.println("Эта строка не выполнится");
}
  1. Создаётся чай за 250, печатается Чай: 250.
  2. setPrice(300): проверка 300 < 0 ложна, исключения нет, цена записана. Печатается Чай: 300.
  3. setPrice(-1000): проверка -1000 < 0 истинна → throw. Метод setPrice обрывается, строка this.price = price не выполняется, цена остаётся 300.
  4. Исключение вылетает из setPrice туда, откуда его вызвали, — в main. В main его никто не перехватывает (как это делать, разберём в уроке про исключения), поэтому main тоже обрывается.
  5. Программа завершается. Последний println не выполняется никогда.

6. Дыра в защите: конструктор

Допустим, сеттер с проверкой уже написан. Всё ли защищено? Посмотри:

Product broken = new Product("Чай", -5);   // проверки нет!

Конструктор записывает значения в поля напрямую, мимо сеттера. Объект рождается испорченным. Значит, проверять нужно и в конструкторе.

7. Лучше сеттера: методы с бизнес-смыслом

Для банковского счёта сеттер setBalance(int) — плохая идея, даже с проверкой «баланс ≥ 0». Почему? Потому что в банке баланс никогда не «устанавливают». Его меняют только конкретные операции, у каждой из которых свои правила:

public class BankAccount {
    private int balance;

    public void deposit(int amount) {        // пополнить
        // правило: сумма пополнения положительна
    }

    public void withdraw(int amount) {       // снять
        // правила: сумма положительна И денег достаточно
    }

    public int getBalance() {                // посмотреть
        return balance;
    }
}

Сравни, как выглядит списание:

  • account.setBalance(account.getBalance() - 300) — проверку «хватает ли денег» должен не забыть сделать каждый, кто так пишет. Кто-то забудет обязательно.
  • account.withdraw(300) — проверка живёт внутри метода, обойти её невозможно. Код ещё и читается как фраза.

Правило на будущее: вместо «установи значение» давай методы, которые называются как действие из реального мира: withdraw, deposit, sell, addStock. В домашке ты напишешь такой счёт полностью.

8. Частые вопросы

Внутри класса тоже надо писать getPrice() вместо price?

Нет. Внутри своего класса поле доступно напрямую, private ограничивает только чужие классы. В методах Product спокойно пиши price.

Можно ли в методе Product обратиться к private-полю другого товара?

Да, и это удивляет многих. private означает «видно в коде этого класса», а не «видно только этому объекту». Поэтому так можно:

public boolean isCheaperThan(Product other) {
    return this.price < other.price;   // other.price — private, но мы внутри Product
}

Я проверил, это компилируется. Это пригодится в домашке для перевода денег между счетами.

Что будет, если вообще не писать модификатор у метода?

Метод будет виден только в своём пакете. Пока все классы урока лежат в одном пакете, разницы не заметно. Как только появятся несколько пакетов (а в Spring-проекте их десятки), всё, что должно вызываться снаружи, придётся сделать public. Привыкай писать модификатор явно и осознанно.

Зачем в toString() был public, а теперь public везде?

Теперь понятно целиком: public — это «доступно отовсюду». toString() обязан быть public, потому что он публичный у Object, а заменить метод более закрытым нельзя. Свои методы, которыми пользуются другие классы, ты делаешь public по собственному решению.

IntelliJ умеет генерировать геттеры и сеттеры. Можно пользоваться?

Можно: Alt+Insert → Getter and Setter. Но в этом уроке и домашке напиши их руками: так закрепится форма. И помни раздел 4: сгенерированный сеттер не содержит проверок, а сеттер есть не у каждого поля.

А если я не хочу, чтобы программа падала от исключения?

Исключение можно перехватить и обработать: показать пользователю сообщение и продолжить работу. Это конструкция try/catch, ей будет посвящён отдельный урок. Пока исключение, которое долетело до конца и уронило программу, — нормальный и честный результат: ты сразу видишь, что и где пошло не так.

9. Проверь себя

Без подглядывания вверх. Ошибся — вернись к нужному разделу.

1. У Product поле private int price, есть getPrice() и setPrice(int). Какая строка в классе Shop не скомпилируется?

Поле private, поэтому из другого класса к нему нельзя обратиться напрямую: price has private access in Product. Методы public, их вызывать можно.

2. Что произойдёт при вызове tea.setPrice(-1) с проверкой из урока?

Проверка срабатывает при выполнении: throw прерывает метод, цена не меняется. Компилятор об отрицательном числе ничего не знает, а метод void ничего не возвращает.

3. Сеттер уже проверяет цену. Зачем проверять её ещё и в конструкторе?

Конструктор записывает поля напрямую, мимо сеттера. Без проверки в нём можно сразу создать new Product("Чай", -5).

4. Метод внутри Product обращается к other.price, где other — другой объект Product, а поле private. Скомпилируется?

private открывает доступ всему коду класса Product, к полям любых объектов этого класса.

5. Какой дизайн банковского счёта правильный?

Баланс меняется только через операции с бизнес-смыслом, у каждой свои правила. Сеттер позволил бы обойти проверку «хватает ли денег».

Шаг 2. BankAccount.java — банковский счёт
