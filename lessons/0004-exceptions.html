Урок 0004 · Java Core · ~90 минут + домашка

Исключения: ошибка, которая не роняет программу

После этого урока ты сможешь перехватить исключение и продолжить работу, выбрать, какие ошибки ловить, и написать собственный класс исключения для своего банковского счёта.

Как читать урок. Устроен так же, как урок 3: после каждого раздела — проверка «Сначала ответь сам, потом открой». В этом уроке главное — поток выполнения: какая строка выполнится следующей. Поэтому трассировок по шагам здесь больше, чем раньше. Проходи их с карандашом: пиши номера строк в том порядке, в каком они выполняются.

Разминка: вспомни урок 3

1. Должок с прошлого раза: что напечатает этот код и какой count обнулился? 
public class Counter {
    private int count = 10;

    public void reset(int count) {
        count = 0;
    }

    public int getCount() {
        return count;
    }
}

Counter c = new Counter();
c.reset(5);
System.out.println(c.getCount());

10. Внутри reset имя count занято параметром, и Java находит его первым. Строка count = 0 обнуляет параметр (копию числа 5), а поле объекта остаётся 10. Чтобы обнулить поле, нужно this.count = 0. IntelliJ подсветит эту строку предупреждением: присвоенное значение нигде не используется.

2. Что происходит с методом, когда выполняется throw?

Метод обрывается сразу. Строки после throw не выполняются, метод ничего не возвращает. Исключение вылетает туда, откуда метод вызвали.

3. Почему в transferTo сначала withdraw, а потом deposit?

withdraw — операция, которая может упасть (не хватает денег). Если она упадёт первой, ничего ещё не изменено. Если бы первым был deposit, получатель уже получил бы деньги, а списание упало бы — «дюп». Правило: сначала то, что может упасть, потом то, что уже не сломается. Сегодня этот вопрос станет важным снова.

1. Проблема: одна ошибка роняет всю программу

До сих пор было так: проверка нашла ошибку → throw → программа завершилась со стеком в консоли. Для домашки это удобно: ты сразу видишь, где ошибка. Но представь настоящий банкомат.

Клиент просит 5000, а на счету 500. Твой withdraw честно бросает исключение. Если его никто не перехватит, упадёт весь банкомат: следующий клиент увидит чёрный экран. А нужно другое: показать «Недостаточно средств» и вернуться в меню.

В backend это ещё важнее. Сервер обрабатывает тысячи запросов. Один пользователь прислал некорректные данные — сервер должен ответить этому пользователю «ошибка в запросе» и продолжить обслуживать остальных. В Spring, к которому мы идём, ответ «400 Bad Request» на неверные данные — это как раз перехваченное исключение.

Значит, нужны два навыка:

  1. Бросить исключение там, где обнаружена ошибка. Это ты уже умеешь (throw).
  2. Поймать его там, где понятно, что делать дальше. Это try/catch — тема урока.

Аналогия: на кухне ресторана повар обнаружил, что кончилась рыба. Он не решает сам, что сказать гостю, и не закрывает ресторан. Он сообщает официанту («рыбы нет» — это и есть исключение), а официант, который знает гостя, предлагает другое блюдо. Ошибку обнаруживает один, а обрабатывает другой — тот, кто знает, как на неё реагировать.

2. Куда летит исключение: стек вызовов

Чтобы понять try/catch, сначала нужно точно знать, куда летит брошенное исключение. Для примеров урока возьмём упрощённый товар. Он не похож на твою домашку, чтобы не подсказывать решение:

Product.java

package demo;

public class Product {
    private String name;
    private int quantity;

    public Product(String name, int quantity) {
        this.name = name;
        this.quantity = quantity;
    }

    public int getQuantity() {
        return quantity;
    }

    public void sell(int amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Количество должно быть больше 0: " + amount);
        }
        if (amount > quantity) {
            throw new OutOfStockException("Нельзя продать " + amount + " шт. «" + name + "», на складе " + quantity);
        }
        quantity = quantity - amount;
    }
}

OutOfStockException («нет в наличии») — наше собственное исключение. Как его написать, разберём в разделе 6. Пока считай, что это такой же класс, как IllegalArgumentException, только с другим именем.

Shop.java

package demo;

public class Shop {
    public static void checkout(Product product, int amount) {
        System.out.println("Оформляю заказ на " + amount + " шт.");
        product.sell(amount);
        System.out.println("Заказ оформлен");
    }
}

Main.java

package demo;

public class Main {
    public static void main(String[] args) {
        Product tea = new Product("Чай", 3);
        System.out.println("1. Начало");
        Shop.checkout(tea, 5);
        System.out.println("2. Конец");
    }
}

Цепочка вызовов: main вызывает checkout, checkout вызывает sell. Java запоминает эту цепочку: каждый вызов кладётся «сверху» на предыдущий, как тарелки в стопке. Эта стопка называется стек вызовов (call stack). Когда метод заканчивается, его тарелка снимается, и выполнение возвращается к тому, кто лежит ниже.

Трассировка запуска. Я запустил этот код на JDK 21:

  1. main: создаётся чай (3 шт.), печатается 1. Начало.
  2. main вызывает checkout(tea, 5). Печатается Оформляю заказ на 5 шт.
  3. checkout вызывает sell(5). Первая проверка 5 <= 0 ложна. Вторая 5 > 3 истинна → throw.
  4. sell обрывается. Строка quantity = quantity - amount не выполняется. Исключение вылетает в checkout, в строку product.sell(amount).
  5. В checkout нет try/catch, поэтому checkout тоже обрывается. Заказ оформлен не печатается. Исключение летит дальше, в main.
  6. В main тоже нет try/catch. main обрывается, 2. Конец не печатается.
  7. Исключение вылетело из main — дальше лететь некуда. Java печатает его и завершает программу.

Вывод программы:

1. Начало
Оформляю заказ на 5 шт.
Exception in thread "main" demo.OutOfStockException: Нельзя продать 5 шт. «Чай», на складе 3
	at demo.Product.sell(Product.java:21)
	at demo.Shop.checkout(Shop.java:6)
	at demo.Main.main(Main.java:7)

Теперь видно, что такое три строки at: это снимок стека вызовов в момент броска. Сверху — где брошено (sell), ниже — кто вызвал (checkout), ещё ниже — кто вызвал его (main). Слово «стек» в «стектрейс» (stack trace) — это и есть та самая стопка вызовов.

demo.OutOfStockException
Тип исключения: пакет demo, класс OutOfStockException. Это наш класс, поэтому без java.lang.
Нельзя продать 5 шт. «Чай»...
Сообщение, которое мы передали при создании исключения.
at demo.Product.sell(Product.java:21)
Строка 21 файла Product.java — сам throw. Где обнаружена ошибка.
at demo.Shop.checkout(Shop.java:6)
Строка 6 в Shop.java — вызов product.sell(amount).
at demo.Main.main(Main.java:7)
Строка 7 в Main.java — вызов Shop.checkout(tea, 5). Откуда всё началось.

Как читать стек на практике. Верхняя строка говорит, где сработала проверка. Но причина часто ниже: кто-то передал плохое значение. Иди сверху вниз, пока не встретишь свой код, который передал неправильный аргумент. В Spring-проекте над твоими строками будут десятки строк из библиотек, и этот навык станет главным.

Проверь себя: что напечатается, если в main вызвать Shop.checkout(tea, 2)?

Исключения нет: 1. Начало, Оформляю заказ на 2 шт., Заказ оформлен, 2. Конец. Стек вызовов просто «разматывается» обычным путём: sell закончился → вернулись в checkout → он закончился → вернулись в main.

3. try/catch: поймать и продолжить

Зачем: чтобы исключение, вылетевшее из метода, не обрывало всё подряд до main, а попало в код, который знает, что с ним делать.

Простыми словами: «попробуй выполнить эти строки (try). Если в них вылетит исключение такого-то типа, поймай его и выполни вот это (catch)».

Python

try:
    checkout(tea, 5)
    print("Продано")
except OutOfStockError as e:
    print("Отказ:", e)

Java

try {
    Shop.checkout(tea, 5);
    System.out.println("Продано");
} catch (OutOfStockException e) {
    System.out.println("Отказ: " + e.getMessage());
}

Идея та же, что в Python: try ↔ try, except ↔ catch, raise ↔ throw. Отличия — фигурные скобки и то, что тип с именем переменной пишутся в круглых скобках: (OutOfStockException e), как параметр метода.

Полный пример, вместо Main из раздела 2:

Main2.java

public class Main2 {
    public static void main(String[] args) {
        Product tea = new Product("Чай", 3);
        System.out.println("1. Начало");
        try {
            System.out.println("2. Пробую продать 5");
            Shop.checkout(tea, 5);
            System.out.println("3. Продано");
        } catch (OutOfStockException e) {
            System.out.println("4. Отказ: " + e.getMessage());
        }
        System.out.println("5. Осталось: " + tea.getQuantity());
    }
}
try {
Начало «опасного» блока. Если внутри вылетит исключение, Java сначала посмотрит на catch ниже, прежде чем обрывать main.
Shop.checkout(tea, 5);
Вызов, внутри которого (глубоко, в sell) может быть брошено исключение. Не важно, на какой глубине: исключение долетит до этого места.
System.out.println("3. Продано");
Выполнится, только если строка выше закончилась без исключения.
} catch (OutOfStockException e) {
«Если вылетело исключение типа OutOfStockException, положи его в переменную e и выполни блок». e — обычная переменная, её можно назвать как угодно, но по традиции пишут e.
e.getMessage()
Метод любого исключения: возвращает текст, переданный при new. Сам стек он не возвращает.
}
Конец catch. После него программа идёт дальше как обычно.
System.out.println("5. Осталось: " ...
Выполнится в любом случае: и после удачной продажи, и после пойманного исключения.

Трассировка по шагам

  1. 1. Начало. Входим в try, печатаем 2. Пробую продать 5.
  2. Вызов checkout → печать Оформляю заказ на 5 шт. → вызов sell(5) → throw.
  3. sell обрывается. В checkout нет try → он тоже обрывается.
  4. Исключение долетело до main, а строка с вызовом стоит внутри try. Java проверяет catch: тип OutOfStockException подходит.
  5. Остаток try пропускается: 3. Продано не печатается. Выполнение прыгает в catch, печатается 4. Отказ: ...
  6. catch закончился, программа идёт дальше: 5. Осталось: 3. Программа завершается нормально, без стека в консоли.

Вывод (проверено на JDK 21):

1. Начало
2. Пробую продать 5
Оформляю заказ на 5 шт.
4. Отказ: Нельзя продать 5 шт. «Чай», на складе 3
5. Осталось: 3

Три правила потока выполнения — запомни их, на этом держится весь урок:

  1. Исключение обрывает каждый метод на своём пути, пока не попадёт в try с подходящим catch.
  2. Внутри try строки после места, где вылетело исключение, не выполняются. Назад в try выполнение не возвращается.
  3. После catch программа продолжается со строки, которая идёт после всей конструкции try/catch.

Что будет, если…

…исключения не было? Весь try выполняется, catch пропускается целиком. Если заказать 2: 1, 2, «Оформляю…», «Заказ оформлен», 3. Продано, 5. Осталось: 1.

…вылетело исключение другого типа? Например, sell(-1) бросит IllegalArgumentException, а catch ловит только OutOfStockException. Тип не подходит → этот catch не срабатывает → main обрывается и программа падает, как в разделе 2. catch ловит только то, что ему указано.

…объявить переменную внутри try, а использовать после? Не скомпилируется. Переменная живёт только внутри своих фигурных скобок, как в теле if или цикла:

try {
    int n = Integer.parseInt("42");
} catch (NumberFormatException e) {
    System.out.println("Не число");
}
System.out.println(n);   // error: cannot find symbol — variable n

В Python это сработало бы, а в Java — нет. Если результат нужен после try, используй его внутри try или объяви переменную до него.

Проверь себя: в Main2 между Shop.checkout и 3. Продано добавили строку System.out.println("2.5");. Напечатается ли она при заказе 5?

Нет. Она стоит в try после места, где вылетело исключение (правило 2). Выполнение сразу прыгает в catch.

4. Несколько catch и семейство исключений

У нашего sell две разные ошибки, и реагировать на них хочется по-разному. «Нет товара» — нормальная ситуация, клиенту надо предложить меньше. «Количество −1» — ошибка в самом заказе. Для этого пишут несколько catch подряд:

Main3.java — касса обрабатывает очередь заказов

public class Main3 {
    public static void main(String[] args) {
        Product tea = new Product("Чай", 3);
        int[] orders = {2, 5, -1, 1};
        for (int amount : orders) {
            try {
                tea.sell(amount);
                System.out.println("Продано " + amount + ", осталось " + tea.getQuantity());
            } catch (OutOfStockException e) {
                System.out.println("Не хватает товара: " + e.getMessage());
            } catch (IllegalArgumentException e) {
                System.out.println("Ошибка в заказе: " + e.getMessage());
            }
        }
        System.out.println("Касса закрыта");
    }
}

Вывод (проверено):

Продано 2, осталось 1
Не хватает товара: Нельзя продать 5 шт. «Чай», на складе 1
Ошибка в заказе: Количество должно быть больше 0: -1
Продано 1, осталось 0
Касса закрыта

Посмотри, что изменилось по сравнению с уроком 3: две плохие заявки не уронили кассу. Цикл дошёл до конца, и последний заказ обслужен. try стоит внутри цикла, поэтому каждый заказ обрабатывается отдельно. Если бы try обнимал весь цикл, первое же исключение выбросило бы нас из цикла в catch, и заказ 1 не обработался бы.

Как Java выбирает catch: проверяет их сверху вниз и выполняет первый подходящий. Остальные пропускает. Сработать может только один.

Что значит «подходящий»: семейство исключений

Классы исключений образуют дерево: каждое исключение — разновидность более общего. Вот часть этого дерева. Я получил её на JDK 21, спрашивая у каждого класса, чьей разновидностью он является:

Throwable                       всё, что можно бросить через throw
├── Error                       сломалась сама JVM (OutOfMemoryError). Не ловят.
└── Exception                   ошибки программы
    ├── IOException             ошибка ввода-вывода (файл, сеть) — checked
    └── RuntimeException        ошибки во время работы — unchecked
        ├── IllegalArgumentException      недопустимый аргумент
        │   └── NumberFormatException     строка не число: Integer.parseInt("abc")
        ├── NullPointerException          вызов метода у null
        └── OutOfStockException           наше (раздел 6)

Правило: catch (X e) ловит исключение типа X и всех его потомков ниже по дереву. Например, catch (IllegalArgumentException e) поймает и NumberFormatException: неправильная строка для числа — тоже разновидность недопустимого аргумента. А catch (RuntimeException e) поймает всё, что под ним, включая наше OutOfStockException.

Аналогия: табличка «вход с животными запрещён» относится и к собакам, и к кошкам, и к таксам. Более общее понятие покрывает все частные.

Почему порядок catch важен

Поставь общий catch выше частного:

try {
    tea.sell(5);
} catch (RuntimeException e) {
    System.out.println("Что-то пошло не так");
} catch (OutOfStockException e) {
    System.out.println("Не хватает товара");
}

Компилятор (JDK 21) откажется:

error: exception OutOfStockException has already been caught

Почему: OutOfStockException — потомок RuntimeException. Первый catch поймает его всегда, и до второго очередь никогда не дойдёт. Java считает недостижимый код ошибкой. Правило: от частного к общему — сначала узкие типы, потом широкие.

В Main3 порядок двух catch не важен: OutOfStockException и IllegalArgumentException — соседи в дереве, а не предок и потомок. Но если бы мы ловили NumberFormatException и IllegalArgumentException, первым обязан был бы стоять NumberFormatException.

Проверь себя: Integer.parseInt("abc") внутри try, ниже только catch (IllegalArgumentException e). Поймается ли исключение?

Да. parseInt бросает NumberFormatException (я проверил: сообщение For input string: "abc"), а это потомок IllegalArgumentException. catch ловит тип и всех потомков.

5. Checked и unchecked: когда компилятор заставляет ловить

В дереве выше две ветки помечены по-разному: IOException — checked, RuntimeException — unchecked. В Python такого разделения нет совсем, это особенность Java.

  • Unchecked (не проверяемые компилятором): RuntimeException и все его потомки, плюс Error. Бросай где хочешь, лови если хочешь — компилятор не следит. Все исключения, которые ты бросал до сих пор, были такими.
  • Checked (проверяемые): всё остальное под Exception, например IOException. Компилятор требует, чтобы метод, где такое исключение может вылететь, либо поймал его через catch, либо явно предупредил в своей сигнатуре словом throws: «я могу это бросить».

Посмотрим на деле. Допустим, OutOfStockException унаследован не от RuntimeException, а от Exception — то есть стал checked. sell не изменился. Компилятор:

Product.java:21: error: unreported exception OutOfStockException; must be caught or declared to be thrown
            throw new OutOfStockException(...);
            ^

Перевод: «необъявленное исключение: его нужно поймать или объявить, что оно бросается». Объявляем в сигнатуре:

public void sell(int amount) throws OutOfStockException {

Теперь Product компилируется, но та же ошибка появляется там, где вызывают sell, если вызов не в try:

Main.java:6: error: unreported exception OutOfStockException; must be caught or declared to be thrown
        tea.sell(5);
                ^

Вызывающий код снова выбирает: поймать или тоже написать throws и передать проблему выше. Так компилятор гарантирует, что про checked-исключение никто не забудет. Обратная сторона: если ловить его негде, слово throws расползается по сигнатурам всей цепочки вызовов.

И наоборот: catch для checked-исключения, которое в try не может вылететь, тоже ошибка — exception IOException is never thrown in body of corresponding try statement. Для unchecked компилятор такого не проверяет.

Что выбрать для своего исключения

Официальный совет Oracle:

«If a client can reasonably be expected to recover from an exception, make it a checked exception. If a client cannot do anything to recover from the exception, make it an unchecked exception.»

Oracle — Unchecked Exceptions: The Controversy

То есть: если вызывающий код может осмысленно восстановиться — checked, если не может — unchecked. На практике в современном backend почти всё делают unchecked. Spring, например, превращает ошибки базы данных в свои unchecked-исключения (DataAccessException — потомок RuntimeException). Причина в том, что ловят ошибки обычно в одном месте на самом верху, а throws через десять слоёв кода только мешает. Поэтому в курсе мы будем писать свои исключения как extends RuntimeException. Но checked нужно уметь читать: стандартная библиотека Java ими полна (файлы, сеть, JDBC).

Проверь себя: почему для throw new IllegalArgumentException(...) в уроке 3 компилятор ни разу не потребовал throws?

IllegalArgumentException — потомок RuntimeException, то есть unchecked. Компилятор такие не отслеживает.

6. Своё исключение

Зачем: по типу исключения вызывающий код решает, что делать (раздел 4). Если всё бросать как IllegalArgumentException, нельзя отдельно поймать «нет товара» и отдельно «заказ на −1». Свой тип даёт ошибке имя.

Вот весь класс OutOfStockException:

public class OutOfStockException extends RuntimeException {
    public OutOfStockException(String message) {
        super(message);
    }
}
public class OutOfStockException
Обычный класс в своём файле OutOfStockException.java. Имя по соглашению заканчивается на Exception.
extends RuntimeException
Новое слово. extends — «расширяет»: наш класс является разновидностью RuntimeException и получает всё, что умеет тот: getMessage(), запись стека, возможность быть брошенным через throw. Так наш класс встаёт в дерево из раздела 4 и становится unchecked. В Python то же самое: class OutOfStockError(Exception):. Наследование целиком — следующая тема, для исключений этого достаточно.
public OutOfStockException(String message) {
Конструктор, принимающий текст сообщения.
super(message);
Новое слово. super(...) вызывает конструктор родителя (RuntimeException) и передаёт ему сообщение. Сохраняет его именно родитель, поэтому потом getMessage() его вернёт. Похоже на this.name = name, только поле хранится в родительской части объекта. Вызов super(...) обязан стоять первой строкой конструктора. Иначе JDK 21 выдаст: call to super must be first statement in constructor.

Использование ничем не отличается от стандартных исключений: throw new OutOfStockException("...") бросает, catch (OutOfStockException e) ловит.

Исключение может нести данные

Исключение — обычный объект. Значит, у него могут быть свои поля и геттеры, как у Product. Тогда catch получит не только текст, но и числа, с которыми можно работать: например, сколько товара всё-таки есть, чтобы предложить клиенту купить столько. Сделать такое исключение для счёта — часть домашки. Подсказка: super(...) всё равно первой строкой, а поля можно присваивать после него.

Проверь себя: что изменится, если написать extends Exception вместо extends RuntimeException?

Исключение станет checked. Метод, который его бросает, обязан будет объявить throws OutOfStockException, а каждый вызывающий — поймать его или тоже объявить throws (раздел 5).

7. Как не надо: три типичные ошибки

Пустой catch — «проглатывание»

try {
    account.withdraw(5000);
} catch (IllegalArgumentException e) {
}

Компилируется и не падает — и это худшее, что может быть. Деньги не сняты, клиент об этом не узнал, в логах пусто. Ошибка исчезла молча, и через неделю ты будешь её искать, не имея ни строчки стека. Если поймал — сделай что-то осмысленное: сообщи пользователю, запиши в лог, верни другой ответ. Если не знаешь, что делать, — не лови, пусть летит выше.

Ловить всё подряд: catch (Exception e)

Поймает и твою ошибку «нет денег», и NullPointerException из-за бага в коде, и вообще всё. Ты напечатаешь «Недостаточно средств», хотя на самом деле в программе баг. Лови конкретные типы, которые ты ожидаешь и знаешь, как обработать.

Исключение вместо обычной проверки

Если можно спокойно проверить заранее (if (product.getQuantity() >= 2)), а ситуация не ошибочная, а просто один из вариантов, — пиши if. Исключения — для исключительных ситуаций, когда метод не может выполнить свою работу. Ими не заменяют обычные ветвления.

8. Частые вопросы

Где ставить try/catch: в sell, в checkout или в main?

Там, где понятно, что делать с ошибкой. sell не знает, кто его вызвал: касса, сайт или склад, — поэтому он только бросает. main в наших примерах «общается с пользователем» и знает, что напечатать. Вспомни повара и официанта из раздела 1. Ловить в том же методе, где бросаешь, обычно бессмысленно: проще было бы написать if.

Можно ли поймать исключение, напечатать и бросить дальше?

Можно: внутри catch написать throw e;. Это пригодится позже, когда будем писать логи. Пока достаточно знать, что так бывает.

Как в catch увидеть стек, а не только сообщение?

e.printStackTrace(); печатает тип, сообщение и все строки at — почти как при падении программы, только программа продолжает работать. Удобно при отладке. В реальном коде вместо этого пишут в лог через библиотеку логирования — до неё ещё дойдём.

Я видел try ... catch ... finally. Что это?

Блок finally выполняется всегда: и после успешного try, и после catch, и даже если исключение не поймано и летит дальше. Нужен, чтобы освободить ресурс — закрыть файл или соединение с базой. Ресурсов у нас пока нет, поэтому сегодня он не нужен. Встретим его вместе с try-с-ресурсами, когда будем подключаться к PostgreSQL через JDBC.

Почему программа на исключении печатает Exception in thread "main", а не просто ошибку?

Программа на Java может выполнять несколько дел параллельно в разных потоках (threads). main работает в потоке с именем "main". Сервер в Spring обрабатывает каждый запрос в своём потоке. Поэтому исключение в одном запросе не роняет весь сервер: Spring ловит его на верху потока.

Что такое NullPointerException, которое я наверняка увижу?

Самое частое unchecked-исключение: вызов метода или обращение к полю через переменную, в которой null. Например, BankAccount x = null; x.getBalance();. Его не ловят — его предотвращают проверкой на null, как ты делал в transferTo. Если оно вылетело, значит в коде баг, и нужно читать стек.

9. Проверь себя

Без подглядывания. Ошибся — вернись к разделу.

1. Исключение брошено в sell, который вызван из checkout, а тот вызван из main внутри try с подходящим catch. Где продолжится выполнение?

Исключение обрывает sell и checkout (в них нет try) и попадает в catch в main. Назад выполнение никогда не возвращается.

2. Чем checked-исключение отличается от unchecked?

Компилятор проверяет, что checked-исключение поймано или объявлено в сигнатуре. Для RuntimeException и его потомков такой проверки нет.

3. Первым стоит catch (RuntimeException e), вторым — catch (IllegalArgumentException e). Что будет?

IllegalArgumentException — потомок RuntimeException, первый catch поймает его всегда. Компилятор: has already been caught. Порядок — от частного к общему.

4. Переменная объявлена внутри try. Можно ли использовать её после блока catch?

Область видимости — фигурные скобки блока, как у if и циклов. Ошибка компиляции cannot find symbol, независимо от того, было ли исключение.

5. Что плохого в catch (Exception e) { } с пустым телом?

Пустой catch «проглатывает» ошибку: ни сообщения, ни стека. А Exception ловит вообще всё, включая баги вроде NullPointerException.

static int parsePositive(String s) {
    System.out.println("A");
    int n = Integer.parseInt(s);
    System.out.println("B");
    if (n <= 0) {
        throw new IllegalArgumentException("не положительное: " + n);
    }
    System.out.println("C");
    return n;
}

public static void main(String[] args) {
    String[] inputs = {"7", "x", "-2"};
    for (String s : inputs) {
        try {
            System.out.println("1");
            int n = parsePositive(s);
            System.out.println("2 " + n);
        } catch (NumberFormatException e) {
            System.out.println("3");
        } catch (IllegalArgumentException e) {
            System.out.println("4 " + e.getMessage());
        }
        System.out.println("5");
    }
}
