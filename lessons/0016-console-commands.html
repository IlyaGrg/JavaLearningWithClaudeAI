Scanner и цикл команд

После урока твой банк станет программой, с которой можно разговаривать: набираешь transfer BANK-1 BANK-2 300, программа отвечает и ждёт следующую команду. Ошибки ввода не роняют программу, а каждая команда покрыта тестом.

Зачем этот урок для backend. Консольный цикл устроен так же, как REST-сервис на Spring: пришёл запрос, его разобрали, вызвали логику, вернули ответ, ошибку превратили в понятное сообщение. Сегодня запрос — строка из консоли, в феврале это будет HTTP-запрос. Главная мысль урока: разбор команд отделён от консоли, поэтому его можно тестировать. На этом же держится контроллер в Spring.

1. Устройство: тонкий Main и класс команд

Весь урок показан на соседнем примере — магазине Shop из урока 15. Банк останется на домашку. Программа будет работать так (это настоящий запуск):

Код делим на три части, и у каждой одна работа:

Почему execute возвращает строку, а не печатает её сам? Тест не умеет набирать текст на клавиатуре и читать экран. А вызвать метод и сравнить строку он умеет: assertEquals("Итого: 140", commands.execute("total")). Всё, что можно вынести из Main, выносим, и тогда почти вся программа проверяется тестами.

Как в Python. Ты бы написал так: while True: line = input("> "), а разбор вынес бы в функцию handle(line) -> str, чтобы проверять её в pytest. Здесь то же самое, только input() заменяет Scanner.

2. Scanner: читаем строку с клавиатуры

Scanner — класс из java.util, который читает текст из источника и разбивает его на куски (Java 21 API: Scanner). Источник клавиатуры — System.in, пара к знакомому System.out.

шаблон

import java.util.Scanner;

Scanner scanner = new Scanner(System.in);   // один раз на всю программу
if (scanner.hasNextLine()) {                  // есть ли ещё строка?
    String line = scanner.nextLine();        // прочитать её целиком
}
new Scanner(System.in)
создаёт сканер поверх клавиатуры. Нужен import java.util.Scanner;
nextLine()
ждёт, пока пользователь нажмёт Enter, и возвращает всю строку без символа перевода строки. Аналог input()
hasNextLine()
возвращает true, если строка есть, и false, если ввод закончился. Ввод заканчивается, когда пользователь нажал Ctrl+D или когда закончились строки, переданные через |

Эксперимент: что будет без hasNextLine

Цикл читает строки и повторяет их. Пользователь ввёл одну строку и нажал Ctrl+D. Угадай, что произойдёт, потом открой.

Scanner scanner = new Scanner(System.in);
while (true) {
    System.out.print("> ");
    String line = scanner.nextLine();
    System.out.println("Вы ввели: " + line);
}
Результат на JDK 21 
> Вы ввели: привет
> Exception in thread "main" java.util.NoSuchElementException: No line found
	at java.base/java.util.Scanner.nextLine(Scanner.java:1660)
	at NoLine.main(NoLine.java:8)

Когда строк больше нет, nextLine() бросает NoSuchElementException. В Python в этом месте был бы EOFError. Поэтому перед каждым nextLine() спрашиваем hasNextLine() и выходим из цикла, если строк нет.

Эксперимент: ловушка nextInt

У сканера есть и nextInt(), который сразу читает число. Пользователь вводит 500, Enter, потом хочет ввести имя. Что окажется в owner?

System.out.print("Сумма: ");
int amount = scanner.nextInt();
System.out.print("Владелец: ");
String owner = scanner.nextLine();
System.out.println("amount = " + amount + ", owner = [" + owner + "]");
Результат на JDK 21 
Сумма: Владелец: amount = 500, owner = []

Программа даже не дала ввести имя. nextInt() забрал из строки 500, но перевод строки после числа остался непрочитанным. nextLine() дочитал этот остаток и вернул пустую строку. На этом спотыкается почти каждый, кто начинает работать со Scanner.

Правило проекта: читаем только nextLine(), а числа достаём из строки сами через Integer.parseInt. Так ловушки просто нет.

3. Разбираем строку на слова

Пользователь ввёл add молоко 90. Нужен массив ["add", "молоко", "90"]: первое слово — команда, остальные — аргументы.

шаблон

String[] parts = line.trim().split("\\s+");
String command = parts[0];
int number = Integer.parseInt(parts[индекс]);
trim()
убирает пробелы в начале и в конце строки
split("\\s+")
режет строку там, где стоит один или больше пробельных символов. Аргумент — регулярное выражение (String.split): \s — любой пробельный символ, + — «один или больше». В Java-строке обратную косую черту пишут дважды, поэтому "\\s+"
Integer.parseInt("90")
превращает текст в int. Если текст не число, бросает NumberFormatException (Integer.parseInt)

Эксперимент: split(" ") против split("\\s+")

Пользователь случайно поставил пробел в начале и два пробела подряд. Угадай, что напечатает каждая строка.

String line = " add  молоко 90";
System.out.println(Arrays.toString(line.split(" ")));
System.out.println(Arrays.toString(line.trim().split("\\s+")));
System.out.println("".trim().split("\\s+").length);
Результат на JDK 21 
[, add, , молоко, 90]
[add, молоко, 90]
1

split(" ") режет по каждому пробелу, поэтому между двумя соседними пробелами получается пустая строка. Команда оказалась бы в parts[1], а не в parts[0]. С trim().split("\\s+") лишних пробелов не важно сколько.

Последняя строка — сюрприз: у пустой строки массив не пустой, а из одного элемента "". Поэтому пустые строки ввода пропускаем ещё в Main, иначе пользователь получит «Неизвестная команда: ».

Хорошая новость про parseInt. NumberFormatException — подкласс IllegalArgumentException. Поэтому catch (IllegalArgumentException e) ловит и неверную цену, и текст вместо числа. Сообщение у него английское: For input string: "девяносто".

4. Класс команд: switch по первому слову

Пишем ShopCommands с нуля. Код растёт от шага к шагу.

  1. Класс и магазин через конструктор. Это внедрение зависимости из урока 6: команды не создают магазин сами, а получают готовый. Так в тесте можно передать свой магазин и потом заглянуть в него.

    public class ShopCommands {
    private final Shop shop;

    public ShopCommands(Shop shop) {
        this.shop = shop;
    }
}

  2. Метод execute: разбить строку и выбрать ветку. Это switch-выражение из урока 13, только по String. Каждая ветка возвращает ответ, а default срабатывает для любой незнакомой команды.

        public String execute(String line) {
        String[] parts = line.trim().split("\\s+");
        return switch (parts[0]) {
            case "add" -> add(parts);
            case "price" -> price(parts);
            case "total" -> "Итого: " + shop.total();
            case "help" -> "Команды: add <товар> <цена>, price <товар>, total, help, exit";
            default -> throw new IllegalArgumentException("Неизвестная команда: " + parts[0]);
        };
    }

    Короткие команды пишем прямо в ветке. Длинные выносим в private-методы, по одному на команду. Иначе switch разрастётся на сто строк.

  3. Проверка числа аргументов. Без неё строка add молоко упадёт на parts[2]. Как именно — смотри эксперимент ниже.

        private static void requireArgs(String[] parts, int count) {
        if (parts.length != count + 1) {
            throw new IllegalArgumentException("Команде " + parts[0] + " нужно аргументов: " + count);
        }
    }

    count + 1 — потому что в parts[0] лежит сама команда. Для add молоко 90 аргументов 2, а длина массива 3.

  4. Метод на каждую команду. Порядок всегда один: проверить число аргументов → достать и преобразовать аргументы → вызвать логику → вернуть ответ.

        private String add(String[] parts) {
        requireArgs(parts, 2);
        String name = parts[1];
        int price = Integer.parseInt(parts[2]);
        shop.addProduct(name, price);
        return "Добавлен товар: " + name + ", " + price;
    }

    private String price(String[] parts) {
        requireArgs(parts, 1);
        String name = parts[1];
        return shop.findPrice(name)
                .map(price -> name + ": " + price)
                .orElse("Нет такого товара: " + name);
    }
default -> throw ...
в switch-выражении ветка может не возвращать значение, а бросать исключение. Компилятор это разрешает
private static void requireArgs
static, потому что метод не трогает поля объекта, ему хватает параметров
parseInt до addProduct
если цена не число, исключение вылетит раньше, чем магазин изменится. Состояние после ошибки не меняется — это четвёртый вопрос из урока 15
.map(price -> ...)
лямбда видит name, потому что переменная не меняется после присваивания (effectively final, урок 11)

Убираем проверку и передаём add молоко, без цены. Ошибку ловим, как в Main, через catch (IllegalArgumentException e). Будет ли поймана?

Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index 2 out of bounds for length 2

ArrayIndexOutOfBoundsException не наследуется от IllegalArgumentException, поэтому мимо catch он пролетает, и программа падает. requireArgs превращает эту ситуацию в понятную ошибку пользователя, которую ловит catch.

5. try-with-resources: закрыть ресурс автоматически

Ресурс — объект, который держит что-то за пределами программы: файл, сетевое соединение, соединение с базой данных, поток ввода. Когда ресурс больше не нужен, его надо закрыть, иначе он остаётся занятым. У таких классов есть метод close(). Сегодня ресурс — Scanner, в уроке 17 будут файлы, в декабре — соединение с PostgreSQL.

шаблон

try (Тип имя = new Ресурс(...)) {
    работа с ресурсом
}   // здесь Java сама вызовет имя.close()
try (...)
в круглых скобках создаётся ресурс. Его тип должен реализовывать интерфейс AutoCloseable — это интерфейс с одним методом close() (AutoCloseable). Scanner его реализует
{ ... }
обычный блок. Переменная ресурса видна только внутри него
}
на выходе из блока Java вызывает close(). Неважно, как блок закончился: дошли до конца, вышли через break или return, вылетело исключение
catch и finally
можно добавить как к обычному try. Они выполнятся уже после закрытия ресурса

без try-with-resources

Scanner scanner = new Scanner(System.in);
try {
    // работа
} finally {
    scanner.close();
}

с try-with-resources

try (Scanner scanner = new Scanner(System.in)) {
    // работа
}

Смысл одинаковый, но во втором варианте закрыть ресурс невозможно забыть (The Java Tutorials: The try-with-resources Statement).

Как в Python. Это with open("file.txt") as f:. Выход из блока with закрывает файл, и выход из блока try (...) тоже. AutoCloseable играет роль метода __exit__.

Эксперимент: в каком порядке всё происходит

Свой класс-ресурс печатает, когда его открыли и закрыли. Ресурсов два, внутри вылетает исключение. Расставь шесть строк вывода по порядку, потом открой.

static class Resource implements AutoCloseable {
    private final String name;

    Resource(String name) {
        this.name = name;
        System.out.println("открыт " + name);
    }

    @Override
    public void close() {
        System.out.println("закрыт " + name);
    }
}

try (Resource a = new Resource("A"); Resource b = new Resource("B")) {
    System.out.println("работаем");
    throw new IllegalStateException("что-то сломалось");
} catch (IllegalStateException e) {
    System.out.println("поймали: " + e.getMessage());
}
Результат на JDK 21 
открыт A
открыт B
работаем
закрыт B
закрыт A
поймали: что-то сломалось

Три вывода:

  • Ресурсы закрываются, даже если вылетело исключение.
  • Закрываются в обратном порядке: последний открытый закрывается первым. Так и должно быть, если B зависит от A.
  • catch выполняется уже после закрытия.

Эксперимент: ресурсом может быть не всё

try (String s = "текст") { ... }
Ошибка компиляции 
error: incompatible types: try-with-resources not applicable to variable type
        try (String s = "текст") {
                    ^
    (String cannot be converted to AutoCloseable)

Строку не нужно закрывать, она не держит ничего снаружи программы. Если видишь эту ошибку, у класса просто нет close().

Эксперимент: два сканера

Первый сканер закрыт через try-with-resources, потом создаём второй. Пользователь набирает в терминале две строки. Прочитает ли второй сканер свою строку?

try (Scanner first = new Scanner(System.in)) {
    System.out.println("первый: " + first.nextLine());
}
Scanner second = new Scanner(System.in);
System.out.println("второй: " + second.nextLine());
Результат на JDK 21 
раз
первый: раз
Exception in thread "main" java.util.NoSuchElementException: No line found
	at java.base/java.util.Scanner.nextLine(Scanner.java:1660)
	at TwoScanners.main(TwoScanners.java:9)

Закрытый сканер закрывает и то, что под ним, — сам System.in. Открыть его заново нельзя. Без try в терминале оба сканера сработали бы. Но если подать ввод через |, второй всё равно упадёт: первый сканер успевает забрать в свой буфер весь ввод сразу.

Правило: один Scanner на System.in на всю программу. Он создаётся в main и закрывается, когда программа заканчивается. Создавать сканер внутри цикла или внутри метода команды нельзя.

6. Main: цикл команд целиком

  1. Подготовка и приветствие.

    public static void main(String[] args) {
    ShopCommands commands = new ShopCommands(new Shop());
    System.out.println("Магазин. Наберите help, чтобы увидеть команды.");
}

  2. Сканер в try-with-resources и бесконечный цикл.

        try (Scanner scanner = new Scanner(System.in)) {
        while (true) {
            System.out.print("> ");
            if (!scanner.hasNextLine()) {
                break;
            }
            String line = scanner.nextLine();
        }
    }
    System.out.println("До свидания!");

    print, а не println: курсор остаётся после > , и пользователь пишет на той же строке. while (true) крутится, пока нас не выкинет break. Первая причина выйти — ввод закончился (Ctrl+D).

  3. Пустая строка и выход.

                if (line.isBlank()) {
                continue;
            }
            if (line.trim().equals("exit")) {
                break;
            }

    continue пропускает остаток тела цикла и сразу начинает следующий круг: снова печатаем > . exit проверяем в Main, а не в ShopCommands, потому что «закончить цикл» — это забота консоли, а не магазина.

  4. Выполнить команду и поймать ошибку пользователя.

                try {
                System.out.println(commands.execute(line));
            } catch (IllegalArgumentException e) {
                System.out.println("Ошибка: " + e.getMessage());
            }

    try стоит внутри цикла. Поймали ошибку, напечатали её, и цикл идёт на следующий круг. Если поставить try снаружи цикла, первая же ошибка завершит программу.

Эксперимент: без catch

Убираем внутренний try/catch, остаётся только System.out.println(commands.execute(line));. Ввод: add молоко 90, add сыр -5, total, exit. Сколько команд выполнится?

Что ловить, а что нет

Ловим только ошибки пользователя: неверные данные, неизвестную команду. Это IllegalArgumentException и исключения твоего банка. А NullPointerException или ArrayIndexOutOfBoundsException — это ошибки в коде. Пусть программа на них падает громко, тогда ты их увидишь и исправишь. catch (RuntimeException e) спрятал бы такие баги за безобидным «Ошибка: null».

В банке исключений несколько: InsufficientFundsException, AccountNotFoundException и другие. Чтобы не перечислять их все в catch, им дают общего родителя — это будет шаг домашки. Тогда ловить можно сразу несколько типов (multi-catch), разделяя их |:

7. Тесты команд

Ради этого мы и отделили ShopCommands от консоли. Тест строит магазин, передаёт строку и сравнивает ответ. Всё как в уроке 15:

class ShopCommandsTest {
    private Shop shop;
    private ShopCommands commands;

    @BeforeEach
    void setUp() {
        shop = new Shop();
        commands = new ShopCommands(shop);
    }

    @Test
    void addPutsProductIntoShop() {
        assertEquals("Добавлен товар: молоко, 90", commands.execute("add молоко 90"));
        assertEquals(90, shop.total());
    }

    @Test
    void extraSpacesAreIgnored() {
        assertEquals("Добавлен товар: молоко, 90", commands.execute("  add   молоко  90 "));
    }

    @Test
    void priceOfMissingProduct() {
        assertEquals("Нет такого товара: сыр", commands.execute("price сыр"));
    }

    @Test
    void totalAfterTwoProducts() {
        commands.execute("add молоко 90");
        commands.execute("add хлеб 50");
        assertEquals("Итого: 140", commands.execute("total"));
    }

    @ParameterizedTest
    @ValueSource(strings = {"add молоко", "add молоко 90 лишнее", "price"})
    void wrongNumberOfArguments(String line) {
        assertThrows(IllegalArgumentException.class, () -> commands.execute(line));
        assertEquals(0, shop.count());
    }

    @Test
    void priceMustBeNumber() {
        IllegalArgumentException e = assertThrows(IllegalArgumentException.class,
                () -> commands.execute("add молоко девяносто"));
        assertEquals("For input string: \"девяносто\"", e.getMessage());
        assertEquals(0, shop.count());
    }

    @Test
    void unknownCommand() {
        IllegalArgumentException e = assertThrows(IllegalArgumentException.class,
                () -> commands.execute("buy молоко"));
        assertEquals("Неизвестная команда: buy", e.getMessage());
    }
}

Интерактивно, как обычную программу:

-q (quiet) убирает строки [INFO], чтобы они не мешали диалогу. exec:java запускает main в том же процессе, что и Maven (exec:java), поэтому клавиатура доходит до твоего Scanner. В IntelliJ тоже работает: зелёный треугольник у main, ввод набирается в окне Run.

Весь сценарий одной командой, без набора руками. printf подаёт строки на вход программы, \n — это Enter:

Весь код целиком

// src/main/java/ru/ilyagrg/shop/ShopCommands.java
package ru.ilyagrg.shop;

public class ShopCommands {
    private final Shop shop;

    public ShopCommands(Shop shop) {
        this.shop = shop;
    }

    public String execute(String line) {
        String[] parts = line.trim().split("\\s+");
        return switch (parts[0]) {
            case "add" -> add(parts);
            case "price" -> price(parts);
            case "total" -> "Итого: " + shop.total();
            case "help" -> "Команды: add <товар> <цена>, price <товар>, total, help, exit";
            default -> throw new IllegalArgumentException("Неизвестная команда: " + parts[0]);
        };
    }

    private String add(String[] parts) {
        requireArgs(parts, 2);
        String name = parts[1];
        int price = Integer.parseInt(parts[2]);
        shop.addProduct(name, price);
        return "Добавлен товар: " + name + ", " + price;
    }

    private String price(String[] parts) {
        requireArgs(parts, 1);
        String name = parts[1];
        return shop.findPrice(name)
                .map(price -> name + ": " + price)
                .orElse("Нет такого товара: " + name);
    }

    private static void requireArgs(String[] parts, int count) {
        if (parts.length != count + 1) {
            throw new IllegalArgumentException("Команде " + parts[0] + " нужно аргументов: " + count);
        }
    }
}
// src/main/java/ru/ilyagrg/shop/Main.java
package ru.ilyagrg.shop;

import java.util.Scanner;

public class Main {
    public static void main(String[] args) {
        ShopCommands commands = new ShopCommands(new Shop());
        System.out.println("Магазин. Наберите help, чтобы увидеть команды.");

        try (Scanner scanner = new Scanner(System.in)) {
            while (true) {
                System.out.print("> ");
                if (!scanner.hasNextLine()) {
                    break;
                }
                String line = scanner.nextLine();
                if (line.isBlank()) {
                    continue;
                }
                if (line.trim().equals("exit")) {
                    break;
                }
                try {
                    System.out.println(commands.execute(line));
                } catch (IllegalArgumentException e) {
                    System.out.println("Ошибка: " + e.getMessage());
                }
            }
        }
        System.out.println("До свидания!");
    }
}

Частые вопросы

Почему после Ctrl+D «До свидания!» печатается на одной строке с >?

Приглашение > уже напечатано без перевода строки, а Ctrl+D перевода строки не добавляет. Если тебя это раздражает, напечатай перед break пустой System.out.println(). На работу программы это не влияет.

Почему Scanner, а не BufferedReader или System.console()?

Для строк с клавиатуры Scanner проще всего. BufferedReader появится в уроке 17 для файлов. System.console() на JDK 21 может вернуть null, когда ввод идёт через | или из IDE, и такой запуск сломался бы.

Зачем закрывать Scanner над System.in, если программа всё равно заканчивается?

Здесь ничего страшного не случится: при выходе из программы операционная система всё освободит сама. Но с файлами и базой данных привычка «открыл — закрой через try-with-resources» обязательна. Мы закрепляем её на простом примере.

Почему exit не одна из веток switch?

execute возвращает строку-ответ, а у exit ответа нет: эта команда означает «прекрати цикл». Цикл живёт в Main, значит, и решение о выходе принимает Main. Есть способы и посложнее, например вернуть из execute объект с флагом «выйти», но для нашего проекта это лишнее.

Можно ли писать команды по-русски, например перевод?

Можно: case "перевод" -> работает, Java 21 по умолчанию читает ввод в UTF-8. Но в консольных программах команды почти всегда английские, как git commit. Оставь английские.

Зачем отдельный репозиторий, если всё и так лежит на GitHub?

Учебный репозиторий — это журнал уроков, а работодатель ищет законченные проекты. У отдельного репозитория своё имя, свой README и своя чистая история коммитов. Ссылку на него можно положить прямо в резюме.

Проверь себя

1. Пользователь ввёл 500 и нажал Enter. Программа вызвала nextInt(), а затем nextLine(). Что вернёт nextLine()?

nextInt() забирает только число. Перевод строки остаётся, и nextLine() дочитывает пустой остаток. Поэтому в проекте читаем только nextLine().

2. Почему execute возвращает строку, а не печатает её сама?

Тест вызывает метод и сравнивает результат через assertEquals. Набирать текст на клавиатуре и читать экран он не умеет.

3. Когда try-with-resources вызывает close()?

Эксперимент с ресурсами A и B: закрыт B и закрыт A напечатались до поймали.

4. Что вернёт "add молоко 90".split(" ") (два пробела после add)?

Между двумя соседними пробелами получается пустая строка. trim().split("\\s+") этого не допускает.

5. Где поставить try/catch, чтобы ошибка в одной команде не завершала программу?

Поймали, напечатали, и цикл пошёл на следующий круг. Снаружи цикла первая же ошибка выкинет из него.
