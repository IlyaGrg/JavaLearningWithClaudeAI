Разминка: вспомни урок 4

1. Должок: исключение было checked, withdraw объявлял throws. Ошибка появилась в transferTo. Почему Main при этом компилировался?

Компилятор требует: checked-исключение надо поймать или объявить. В твоём Main оба вызова, withdraw в цикле банкомата и transferTo, уже стояли внутри try с catch (InsufficientFundsException e). Значит, исключение там поймано, и требование выполнено. А в transferTo вызов withdraw(amount) стоял без try и без throws — поэтому ошибка была только там. Если бы ты добавил throws в transferTo, Main всё равно скомпилировался бы по той же причине.

2. Кто это сообщает — компилятор или запущенная программа? (а) cannot find symbol; (б) Exception in thread "main" ...; (в) строки 1 A 3 5.

(а) компилятор, javac: программа ещё даже не запускалась. (б) и (в) — запущенная программа, java. Компилятор никогда не печатает вывод твоего кода, он только проверяет его и собирает .class.

3. Ты писал InsufficientFundsException extends RuntimeException. Что твой класс получил от RuntimeException, хотя ты этого не писал?

Метод getMessage(), запись стека вызовов, возможность быть брошенным через throw и пойманным через catch (RuntimeException e). Ты написал только поля и геттеры, а всё остальное унаследовал. Сегодня разберём, как это работает.

1. Проблема: почти одинаковые классы

В магазине есть обычные товары и товары со скидкой. Вот обычный товар — упрощённый Product из прошлых уроков:

Product.java

package demo;

public class Product {
    private String name;
    private int price;

    public Product(String name, int price) {
        if (price < 0) {
            throw new IllegalArgumentException("Цена не может быть отрицательной: " + price);
        }
        this.name = name;
        this.price = price;
    }

    public String getName() {
        return name;
    }

    public int getPrice() {
        return price;
    }

    public int getFinalPrice() {
        return price;
    }

    @Override
    public String toString() {
        return name + ": " + getFinalPrice() + " руб.";
    }
}

getFinalPrice() — «сколько заплатит покупатель». У обычного товара это просто цена.

Теперь нужен товар со скидкой: у него всё то же самое — название, цена, проверка цены, геттеры — плюс процент скидки, а итоговая цена считается по-другому. Первое, что приходит в голову, — скопировать Product в DiscountedProduct и дописать. Получится два класса, на 80% одинаковых. Чем это плохо, ты уже знаешь по уроку 3, где правило «одна проверка — одно место» привело к checkPrice:

  • Поменялось правило цены — правишь в двух местах и однажды забываешь одно.
  • Метод cartTotal(ArrayList<Product> cart) не примет товар со скидкой: это другой тип. Придётся писать вторую корзину и второй метод.

Второе хуже первого. Нам нужно сказать Java: «товар со скидкой — это тоже товар, просто особый». Для этого и есть наследование.

2. extends: «является разновидностью»

Простыми словами: класс-потомок (subclass) получает всё, что есть у класса-родителя (superclass), и добавляет своё или меняет поведение.

Python

class DiscountedProduct(Product):
    ...

Java

public class DiscountedProduct extends Product {
    ...
}

Идея та же, что в Python: родитель указывается при объявлении класса. Различие одно и важное: в Java у класса ровно один родитель. Написать extends Product, Something нельзя: JDK 21 ответит '{' expected — после первого имени он ждёт начало тела класса.

Вот весь потомок. Дальше разберём его по частям:

DiscountedProduct.java

package demo;

public class DiscountedProduct extends Product {
    private int discountPercent;

    public DiscountedProduct(String name, int price, int discountPercent) {
        super(name, price);
        if (discountPercent < 0 || discountPercent > 100) {
            throw new IllegalArgumentException("Скидка от 0 до 100: " + discountPercent);
        }
        this.discountPercent = discountPercent;
    }

    public int getDiscountPercent() {
        return discountPercent;
    }

    @Override
    public int getFinalPrice() {
        return getPrice() - getPrice() * discountPercent / 100;
    }

    @Override
    public String toString() {
        return super.toString() + " (скидка " + discountPercent + "%)";
    }
}

Что важно: в этом классе нет полей name и price, нет getName() и getPrice(). Но они работают:

DiscountedProduct coffee = new DiscountedProduct("Кофе", 800, 25);
System.out.println(coffee.getName() + " " + coffee.getPrice());   // Кофе 800

Эти методы унаследованы от Product. Объект coffee внутри состоит из двух частей: «часть Product» (name, price) и «часть DiscountedProduct» (discountPercent). Это один объект, а не два.

Проверка «является ли»

Наследование уместно, только если фраза «Потомок — это разновидность Родителя» звучит правдой:

  • «Товар со скидкой — это товар» ✓
  • «InsufficientFundsException — это RuntimeException» ✓
  • «Корзина — это товар» ✗ — корзина содержит товары. Для этого есть поле ArrayList<Product>, а не extends.

Общий предок всех классов: Object

Если extends не написан, Java сама подставляет extends Object. Поэтому у любого объекта есть методы toString(), equals() и ещё несколько: они унаследованы от Object. Это ответ на твой вопрос из урока 2, откуда взялся toString. Без переопределения Object.toString() печатает имя класса и хеш-код. Я проверил: класс без своего toString печатает что-то вроде demo.Plain@2a139a55.

Источник: Oracle — Inheritance, Object as a Superclass.

Проверь себя: в DiscountedProduct нет метода getName(). Почему coffee.getName() компилируется?

getName() объявлен в Product как public, а DiscountedProduct extends Product его унаследовал. Java ищет метод сначала в классе объекта, потом у родителя, потом у родителя родителя — вплоть до Object.

3. Конструктор потомка и super(...)

Конструкторы не наследуются. У DiscountedProduct свой конструктор, и он отвечает за весь объект, включая «часть Product». Но поля name и price — private в Product, а проверка цены живёт в конструкторе Product. Поэтому потомок не заполняет их сам, а просит родителя: super(name, price).

public DiscountedProduct(String name, int price, int discountPercent) {
Конструктор потомка принимает всё: и данные для родителя, и своё.
super(name, price);
Вызвать конструктор родителя Product(String, int). Он проверит цену и заполнит name и price. Ты уже писал super(message) в своём исключении — это то же самое. Должен стоять первой строкой.
if (discountPercent < 0 || ...) { throw ... }
Проверка своего поля. Её можно делать только после super.
this.discountPercent = discountPercent;
Заполняем своё поле, как обычно.

Трассировка: new DiscountedProduct("Кофе", 800, 25)

  1. Java выделяет память под объект целиком, со всеми полями обоих классов.
  2. Запускается конструктор DiscountedProduct. Первая строка — super("Кофе", 800).
  3. Выполнение переходит в конструктор Product: проверка 800 < 0 ложна, name = "Кофе", price = 800. Конструктор Product закончился.
  4. Возвращаемся в конструктор DiscountedProduct, на строку после super: проверка скидки, discountPercent = 25.
  5. Конструктор закончился, new возвращает ссылку на готовый объект.

Если бы цена была -5, на шаге 3 вылетело бы исключение из конструктора Product, и по правилам урока 4 оно оборвало бы и конструктор DiscountedProduct. Объект не был бы создан. Проверку цены потомок получил бесплатно.

Что будет, если не написать super(...)

Тогда Java сама подставит первой строкой super() — вызов конструктора родителя без аргументов. Но у Product такого конструктора нет, есть только Product(String, int). JDK 21:

error: constructor Product in class Product cannot be applied to given types;
  required: String,int
  found:    no arguments
  reason: actual and formal argument lists differ in length

Читается так: «конструктор Product требует String, int, а вызван без аргументов». Ошибка указывает на конструктор потомка, хотя super() ты там не писал: его подставила Java. Если увидишь такое — значит, забыл super(...).

Проверь себя: почему в конструкторе потомка нельзя просто написать this.name = name;?

name объявлен private в Product, а private — доступ только из кода самого класса Product (урок 3). Код потомка — это другой класс. Ну и проверки родителя при этом обошлись бы. Поэтому — через super(name, price).

4. private у родителя: наследуется, но не видно

Поле price лежит внутри объекта coffee (вспомни схему), но код DiscountedProduct обратиться к нему по имени не может:

@Override
public int getFinalPrice() {
    return price / 2;      // error: price has private access in Product
}

Это та же ошибка, что в уроке 3, когда ты пробовал account.balance = ... из Main. Для private потомок — такой же «чужой» класс. Поэтому в DiscountedProduct мы пишем getPrice(): публичный геттер родителя доступен.

И это хорошо, а не неудобство. Родитель сам охраняет свои инварианты («цена ≥ 0»), и ни один потомок не сможет их сломать, даже случайно.

protected из таблицы урока 3 — модификатор «видно потомкам (и пакету)». Если бы price был protected, потомок мог бы писать price напрямую — но и менять его в обход проверок. Поэтому поля оставляют private, а protected используют редко, для методов, специально предназначенных потомкам.

5. Переопределение и @Override

Переопределение (overriding) — потомок пишет метод с той же сигнатурой, что у родителя (то же имя, те же типы параметров), и даёт ему своё поведение. Для объектов-потомков будет выполняться новая версия.

В DiscountedProduct переопределены два метода:

@Override public int getFinalPrice() { return getPrice() - getPrice() * discountPercent / 100; }
Та же сигнатура, что у Product.getFinalPrice(), своё тело: цена минус скидка. getPrice() — унаследованный геттер.
@Override public String toString() { return super.toString() + " (скидка " + discountPercent + "%)"; }
super.toString() — «вызови родительскую версию этого метода». Мы не повторяем код родителя, а дописываем к его результату свой текст. super.метод() можно писать в любом месте метода, не только первой строкой.

Не путай: переопределение и перегрузка

В глоссарии из урока 1 уже стояла пометка: перегрузка — это другое.

Перегрузка (overloading)Переопределение (overriding)
Гдев одном классев потомке, для метода родителя
Сигнатураимя то же, параметры разныеимя и параметры те же
Примерmax(int, int) и max(double, double)getFinalPrice() в Product и в DiscountedProduct

Зачем @Override

Ты спрашивал об этом ещё в уроке 2. @Override — аннотация, пометка для компилятора: «я собираюсь переопределить метод родителя, проверь». Программа работает и без неё. Но посмотри, что бывает с опечаткой.

С @Override: написал getFinalprice (маленькая p):

error: method does not override or implement a method from a supertype
    @Override
    ^

Компилятор сразу сказал: у родителя такого метода нет, ты ничего не переопределяешь.

Без @Override: та же опечатка компилируется. Java считает getFinalprice новым, отдельным методом потомка. Я проверил: товар за 400 с «половинной» ценой в таком классе печатает 400. Вызывается родительский getFinalPrice(), а твой метод не вызывает никто. Ни ошибки, ни предупреждения при запуске — тихий баг, как с price = price из прошлых уроков.

Вывод: ставь @Override всегда, когда переопределяешь. Это бесплатная проверка.

Источник: Oracle — Overriding and Hiding Methods, Override (Java 21).

Правило доступа

Переопределённый метод не может быть «закрытее» родительского. Если у родителя public int getFinalPrice(), а у потомка без public:

error: getFinalPrice() in Narrow cannot override getFinalPrice() in Product
  attempting to assign weaker access privileges; was public

Логика: везде, где можно вызвать метод у товара, его должно быть можно вызвать и у товара со скидкой. Это же объясняет, почему toString() обязан быть public — у Object он public.

Проверь себя: зачем в toString() потомка super.toString(), а не просто toString()?

Просто toString() внутри toString() вызвал бы сам себя — снова и снова, пока не кончится стек вызовов (StackOverflowError). super. явно говорит: нужна версия родителя.

6. Полиморфизм: какой метод выполнится

Самое ценное в наследовании. Раз товар со скидкой — это товар, его можно положить туда, где ждут товар:

Product p = new DiscountedProduct("Кофе", 800, 25);   // ✓ компилируется

ArrayList<Product> cart = new ArrayList<>();
cart.add(new Product("Чай", 250));
cart.add(new DiscountedProduct("Кофе", 800, 25));      // ✓ тоже товар
cart.add(new DiscountedProduct("Печенье", 120, 50));

Теперь главный вопрос: p.getFinalPrice() — какую версию вызовет Java? Переменная типа Product, а объект — DiscountedProduct.

Два правила полиморфизма:

  1. Какие методы можно вызвать — решает тип переменной. Проверяет компилятор.
  2. Какая версия выполнится — решает тип объекта. Решает запущенная программа, в момент вызова.

Применим к p.getFinalPrice():

  1. Компиляция: у типа Product есть getFinalPrice()? Да → компилируется.
  2. Выполнение: Java смотрит по ссылке на настоящий объект. Это DiscountedProduct, у него есть своя версия → выполняется она. Результат 600 (проверено).

Аналогия: на кассе висит табличка «Оплата картой». Кассир (переменная типа «карта») знает только, что карту можно приложить. Но списание пройдёт по правилам конкретной карты, которую ты дал: кешбэк, кредитный лимит — у каждой свои. Кассиру знать это не нужно.

Корзина — тот самый cartTotal

int total = 0;
for (Product p : cart) {
    total = total + p.getFinalPrice();
}
System.out.println("Итого: " + total);    // Итого: 910

Проверим 910: чай 250 (обычный) + кофе 600 (800 − 25%) + печенье 60 (120 − 50%) = 910 ✓. Цикл написан один раз и ничего не знает о скидках. Каждый объект сам отвечает, сколько он стоит. Завтра появится WeightProduct с ценой за килограмм — цикл менять не придётся.

Полиморфизм работает даже внутри родителя

Посмотри внимательно на Product.toString(): там getFinalPrice(), а не price. Трассировка System.out.println(coffee):

  1. println вызывает coffee.toString(). Объект — DiscountedProduct → его версия.
  2. Она вызывает super.toString() → выполняется код Product.toString().
  3. В нём вызывается getFinalPrice(). Это вызов у this, а this — всё тот же объект DiscountedProduct. По правилу 2 выполняется версия потомка → 600.
  4. Product.toString() возвращает "Кофе: 600 руб.", потомок дописывает " (скидка 25%)".

Итог (проверено): Кофе: 600 руб. (скидка 25%). Код родителя был написан до того, как появились скидки, а работает с ними правильно.

Чего нельзя: правило 1 в действии

Product p = new DiscountedProduct("Кофе", 800, 25);
p.getDiscountPercent();   // error: cannot find symbol
                          //   symbol:   method getDiscountPercent()
                          //   location: variable p of type Product

Объект внутри умеет getDiscountPercent(), но компилятор смотрит на тип переменной: у Product такого метода нет. Обрати внимание на location: variable p of type Product — компилятор прямо говорит, на что он смотрел. Если нужен метод потомка, храни объект в переменной типа потомка: DiscountedProduct coffee = ....

Проверь себя: Product x = new Product("Сыр", 400); — что вернёт x.getFinalPrice()? А если затем сделать x = new DiscountedProduct("Сыр", 400, 10);?

Сначала 400: объект — обычный Product. После присваивания переменная ссылается на другой объект, DiscountedProduct, и тот же вызов вернёт 360. Переменная одна, а выполняемый метод зависит от объекта, на который она сейчас ссылается.

7. Когда наследование — плохая идея

  • Не наследуй ради того, чтобы переиспользовать пару методов. Если не проходит проверка «является разновидностью», лучше сделай поле нужного типа и вызывай его методы. Это называется композиция. Корзина содержит товары, магазин содержит корзины.
  • Потомок не должен ломать обещания родителя. Если код работает с Product и рассчитывает, что getFinalPrice() ≥ 0, потомок не должен возвращать минус. Иначе полиморфный цикл из раздела 6 начнёт давать неверные итоги.
  • Цепочки наследования делай короткими. Один-два уровня под своим классом — нормально. Пять уровней — читать такой код никто не сможет.

8. Частые вопросы

Можно ли переопределить конструктор?

Нет. Конструкторы не наследуются, поэтому и переопределять нечего. У каждого класса свои конструкторы, и потомок вызывает родительский через super(...).

Проверка в конструкторе потомка стоит после super. Значит, на время объект «наполовину неправильный»?

На время выполнения конструктора — да. Но если проверка бросит исключение, new не вернёт ссылку, и никто снаружи этот объект не увидит. Как в уроке 4: исключение обрывает конструктор, объект не создан.

Как это в Python? Там super().__init__(...).

Да, это то же самое. Разница в том, что в Python вызов родительского __init__ можно забыть, и поля родителя просто не появятся. В Java компилятор следит за этим: либо ты вызываешь super(...) сам, либо он подставит super() и потребует, чтобы такой конструктор существовал.

Можно ли запретить наследоваться от моего класса?

Да, словом final: public final class Money. Так сделан, например, String — от него нельзя унаследоваться. Метод тоже можно сделать final, тогда его нельзя переопределить.

В Spring я буду писать extends?

Своё — редко. В современном backend больше используют интерфейсы, это тема следующего урока. Но механика из этого урока — переопределение, @Override, «метод выбирается по объекту» — нужна там на каждом шагу. Например, ты постоянно будешь переопределять toString(), equals() и hashCode() от Object. И, как ты уже видел, все исключения устроены через extends.

Можно ли у переопределённого метода изменить параметры?

Тогда это уже не переопределение, а новый метод (перегрузка). Именно такую ошибку ловит @Override.

9. Проверь себя

Без подглядывания. Ошибся — вернись к разделу.

1. Product p = new DiscountedProduct("Кофе", 800, 25); Какая версия p.getFinalPrice() выполнится?

Версия выбирается по объекту, на который ссылается переменная (правило 2). Присвоить потомка переменной типа родителя можно: товар со скидкой — это товар.

2. Зачем писать @Override?

Переопределение работает и без аннотации. @Override — проверка: при опечатке в имени или параметрах будет ошибка компиляции, а не тихий баг.

3. Какая строка в методе DiscountedProduct не скомпилируется? (price и name — private в Product)

private-поле родителя недоступно по имени в коде потомка: price has private access in Product. Публичные методы родителя — пожалуйста.

4. В конструкторе потомка нет super(...), а у Product есть только конструктор (String, int). Что будет?

Java подставит super() без аргументов, а такого конструктора у Product нет: constructor Product in class Product cannot be applied to given types.

5. Product p = new DiscountedProduct("Кофе", 800, 25); Что будет при p.getDiscountPercent()?

Какие методы можно вызвать, решает тип переменной (правило 1): cannot find symbol ... location: variable p of type Product.
