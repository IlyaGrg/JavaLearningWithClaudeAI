Урок 0006 · Java Core · ~90 минут + домашка

Интерфейсы: договориться об умении, а не о родителе

После этого урока ты сможешь объявить интерфейс, реализовать его в нескольких классах, написать сервис, который работает с любой реализацией, и научить свои объекты сортироваться стандартным Collections.sort.

Зачем этот урок для backend. Spring-приложение почти целиком построено на интерфейсах: сервис получает «что-то, что умеет сохранять в базу» или «что-то, что умеет отправлять письма», и не знает, какой именно класс это делает. В разделе 5 ты руками сделаешь то, что Spring делает автоматически. Когда дойдём до Spring, это будет уже знакомая идея, а не магия.

Разминка: вспомни урок 5

1. Потомок переопределил withdraw и проверяет в нём только лимит. Выполнится ли код родительского withdraw?

Нет. Переопределение заменяет метод целиком. Чтобы выполнить и версию родителя, нужно явно вызвать super.withdraw(amount). Ты сам поймал этот баг в домашке: снятие ничего не списывало.

2. BankAccount a = new SavingsAccount(...). Что решает тип переменной, а что — тип объекта?

Тип переменной — какие методы можно вызвать (проверяет компилятор). Тип объекта — какая версия выполнится (решается при выполнении). Сегодня эти же два правила будут работать для интерфейсов.

3. Сколько родителей может быть у класса в Java?

Ровно один (extends принимает одно имя). Если не написан — Object. Запомни это ограничение: интерфейсы во многом нужны, чтобы его обойти.

1. Проблема: общее умение без общего родителя

Магазин после оформления заказа должен уведомить покупателя. Способов несколько: SMS, письмо, позже Telegram. Код оформления заказа пишется один раз и не должен меняться, когда добавляется новый способ.

Попробуем наследованием. Что общего у SMS и письма? Оба умеют отправить сообщение. Но «письмо — это разновидность SMS»? Нет. Проверка «является разновидностью» из урока 5 не проходит. Можно придумать общего родителя Notifier, но:

  • у него нет никакого общего кода: SMS и письмо отправляются совершенно по-разному. Родитель был бы пустым классом с методом, который ничего не делает;
  • родитель у класса один. Если EmailNotifier уже наследуется от чего-то нужного (например, от класса почтовой библиотеки), второго родителя ему не дать.

Нам не нужен общий родитель. Нам нужен общий договор: «кто бы ты ни был, у тебя есть метод send(получатель, текст)». Это и есть интерфейс.

Аналогия — розетка. Стандарт розетки описывает только форму: два штыря, такое-то расстояние. Что подключено — чайник, зарядка, лампа — розетке не важно. Любой прибор, сделанный по стандарту, работает с любой розеткой. Интерфейс — это стандарт, а классы — приборы.

2. Объявляем интерфейс

Notifier.java

package demo;

public interface Notifier {
    void send(String recipient, String message);
}
public interface Notifier {
interface вместо class. Файл называется Notifier.java, как и для класса. Имя обычно описывает умение или роль: Notifier («уведомитель»), Comparable («сравнимый»).
void send(String recipient, String message);
Метод без тела: после скобок сразу ;, фигурных скобок нет. Это только обещание: «у каждого, кто реализует Notifier, будет такой метод». Как он работает, решит каждый класс сам. Такой метод называется абстрактным.
}
Всё. Полей с данными, конструкторов и кода здесь нет.

Обрати внимание: у send не написано public. Методы интерфейса автоматически public — договор нужен, чтобы им пользовались снаружи, так что закрытым он быть не может. Это пригодится в разделе 3.

Python

from abc import ABC, abstractmethod

class Notifier(ABC):
    @abstractmethod
    def send(self, recipient, message):
        ...

Java

public interface Notifier {
    void send(String recipient,
              String message);
}

В Python чаще всего обходятся вообще без этого: если у объекта есть метод send, его можно вызвать (так называемая «утиная типизация»). Java строже: класс должен явно пообещать, что выполняет договор, и компилятор проверит, что обещание выполнено.

Источник: Oracle — Defining an Interface.

3. implements: класс выполняет договор

SmsNotifier.java

package demo;

public class SmsNotifier implements Notifier {
    @Override
    public void send(String recipient, String message) {
        System.out.println("[SMS → " + recipient + "] " + message);
    }
}

EmailNotifier.java

package demo;

public class EmailNotifier implements Notifier {
    private String from;

    public EmailNotifier(String from) {
        this.from = from;
    }

    @Override
    public void send(String recipient, String message) {
        System.out.println("[Email от " + from + " для " + recipient + "] " + message);
    }
}
implements Notifier
«Реализует Notifier»: класс обещает, что у него есть все методы интерфейса. Для класса — extends, для интерфейса — implements.
@Override
Та же аннотация, что в уроке 5, с той же пользой: опечатка в имени или параметрах станет ошибкой компиляции.
public void send(...) { ... }
Реализация обещанного метода. Сигнатура та же, что в интерфейсе, и обязательно public.
private String from; public EmailNotifier(String from)
Свои поля и конструктор — сколько угодно. Интерфейс требует только наличия send, остальное — дело класса.

Что компилятор проверяет

Забыл реализовать метод. Класс написал implements Notifier, а send не написал. JDK 21:

error: Lazy is not abstract and does not override abstract method send(String,String) in Notifier
public class Lazy implements Notifier {
       ^

Читается так: «Lazy не выполнил обещание: нет метода send(String,String) из Notifier». Слова «is not abstract» пока пропусти, они про абстрактные классы (см. частые вопросы).

Реализовал без public.

error: send(String,String) in Weak cannot implement send(String,String) in Notifier
  attempting to assign weaker access privileges; was public

Это то же правило, что в уроке 5: нельзя сделать метод «закрытее», чем в договоре. А в интерфейсе метод public, хотя слово и не написано.

Попробовал создать объект интерфейса.

Notifier n = new Notifier();
// error: Notifier is abstract; cannot be instantiated

Логично: у send нет тела, выполнять было бы нечего. Нельзя купить «стандарт розетки», можно купить только прибор по стандарту.

Проверь себя: в интерфейсе три метода, класс реализовал два. Скомпилируется?

Нет. Обещание — все методы интерфейса. Ошибка ... does not override abstract method ... назовёт тот, которого не хватает.

4. Интерфейс как тип переменной

Объект интерфейса создать нельзя, но переменная типа интерфейса — можно. В неё кладут объект любого класса, который его реализует:

Notifier n = new SmsNotifier();
n.send("Илья", "Привет");                // [SMS → Илья] Привет

Здесь работают те же два правила, что в уроке 5:

  1. Какие методы можно вызвать — по типу переменной. У Notifier есть только send, значит, через n можно вызвать только send.
  2. Какая версия выполнится — по объекту. Объект SmsNotifier — выполняется его send.

Список «всех способов уведомить» — тоже через тип интерфейса:

ArrayList<Notifier> all = new ArrayList<>();
all.add(new SmsNotifier());
all.add(new EmailNotifier("shop@example.com"));
for (Notifier x : all) {
    x.send("Валерия", "Скидка 10% до пятницы");
}

Вывод (проверено на JDK 21):

[SMS → Валерия] Скидка 10% до пятницы
[Email от shop@example.com для Валерия] Скидка 10% до пятницы

Классы SmsNotifier и EmailNotifier друг с другом никак не связаны — у них разные поля и нет общего родителя, кроме Object. Но оба выполняют договор Notifier, и этого достаточно, чтобы лежать в одном списке.

Проверь себя: Notifier n = new EmailNotifier("a@b.ru"); — можно ли вызвать у n метод, который есть только у EmailNotifier?

Нет, по правилу 1: компилятор смотрит на тип переменной, а у Notifier такого метода нет. Будет cannot find symbol, как в уроке 5 с getDiscountPercent().

5. Главное: сервис зависит от интерфейса

Теперь соберём то, ради чего всё затевалось. Сервис заказов:

OrderService.java

package demo;

public class OrderService {
    private Notifier notifier;

    public OrderService(Notifier notifier) {
        this.notifier = notifier;
    }

    public void placeOrder(String customer, Product product) {
        System.out.println("Оформлен заказ: " + product);
        notifier.send(customer, "Ваш заказ «" + product.getName() + "» принят");
    }
}
private Notifier notifier;
Поле типа интерфейса. Сервис знает только, что у этого объекта есть send. Ни слова про SMS или email.
public OrderService(Notifier notifier)
Уведомитель сервису передают снаружи через конструктор, сам сервис его не создаёт. Это ключевой момент.
notifier.send(customer, ...)
Вызов по договору. Какой send выполнится, зависит от объекта, который передали в конструктор (правило 2).

Использование:

OrderService sms = new OrderService(new SmsNotifier());
sms.placeOrder("Илья", new Product("Чай", 250));

OrderService email = new OrderService(new EmailNotifier("shop@example.com"));
email.placeOrder("Илья", new Product("Кофе", 800));

Вывод (проверено):

Оформлен заказ: Чай: 250 руб.
[SMS → Илья] Ваш заказ «Чай» принят
Оформлен заказ: Кофе: 800 руб.
[Email от shop@example.com для Илья] Ваш заказ «Кофе» принят

Что мы получили:

  • Новый способ уведомления — новый класс, а не правка сервиса. Появится Telegram — пишешь TelegramNotifier implements Notifier, и OrderService не меняется ни на строчку.
  • Сервис можно проверить без настоящих SMS. Передай ему «поддельный» уведомитель, который ничего не отправляет, а только запоминает, что его просили отправить. Потом посмотри: просили? кому? какой текст? Такой класс называют фейком (fake). Так устроены автоматические тесты, до которых мы дойдём с JUnit. В домашке ты напишешь такой фейк сам.

Это и есть то, что делает Spring

Приём «объект не создаёт то, что ему нужно, а получает это через конструктор» называется внедрение зависимости (dependency injection). Notifier — зависимость OrderService. Сейчас мы внедряем её руками: new OrderService(new SmsNotifier()). В Spring ты напишешь только класс OrderService с таким же конструктором, а нужный объект Spring найдёт и передаст сам. Именно поэтому в Spring-проектах так много интерфейсов.

Источник: Spring Framework — Dependency Injection (заглядывать пока рано, но приятно знать, что это та же идея).

Проверь себя: почему в OrderService поле типа Notifier, а не SmsNotifier?

С полем SmsNotifier сервис умел бы работать только с SMS: передать ему EmailNotifier или фейк было бы нельзя, типы не совпадут. Тип интерфейса принимает любую реализацию.

6. Интерфейс из JDK: Comparable и сортировка

Интерфейсы пишешь не только ты. Стандартная библиотека Java полна ими, и самый частый на практике — Comparable, «сравнимый». Проблема: как отсортировать список товаров? Collections.sort(cart) — готовый метод сортировки. Но откуда ему знать, какой товар «меньше»: по цене? по названию?

Ответ: Collections.sort требует, чтобы элементы списка реализовывали Comparable. Это договор: «у меня есть метод compareTo, который скажет, кто из нас двоих меньше».

public class Product implements Comparable<Product> {
    private String name;
    private int price;

    // конструктор, геттеры, toString — как раньше

    @Override
    public int compareTo(Product other) {
        return Integer.compare(this.price, other.price);
    }
}
implements Comparable<Product>
«Товар сравним с товаром». В угловых скобках — с чем сравниваем, как в ArrayList<Product> — что храним. Без них compareTo принимал бы любой Object.
public int compareTo(Product other)
Единственный метод договора. Сравнивает this с other.
Integer.compare(this.price, other.price)
Готовый метод сравнения двух чисел. Возвращает отрицательное, если первое меньше, 0, если равны, положительное, если больше. Ровно это и требует договор compareTo.

Я проверил: для чая (250) и кофе (800) tea.compareTo(coffee) даёт -1, coffee.compareTo(tea) — 1, а чай против мёда за те же 250 — 0.

ArrayList<Product> cart = new ArrayList<>();
cart.add(new Product("Кофе", 800));
cart.add(new Product("Чай", 250));
cart.add(new Product("Печенье", 120));
Collections.sort(cart);                  // нужен import java.util.Collections;
System.out.println(cart);
// [Печенье: 120 руб., Чай: 250 руб., Кофе: 800 руб.]

Посмотри, что произошло. Метод Collections.sort написан разработчиками Java много лет назад. Про твой Product он ничего не знает. Но он вызывает compareTo у элементов через тип Comparable — и выполняется твоя версия (правило 2). Чужой код работает с твоим классом, потому что вы договорились через интерфейс.

Что будет без implements Comparable? Collections.sort(list) не скомпилируется. Сообщение у JDK 21 длинное и страшное, но главное в первых строках:

error: no suitable method found for sort(ArrayList<Unsortable>)
    ...
        upper bounds: Comparable<? super T#1>)

«Подходящего sort нет», а ниже мелькает Comparable: компилятор подсказывает, чего не хватает. Остальное — подробности про generics, их разберём в отдельном уроке.

Источник: Comparable (Java 21), Collections (Java 21).

Проверь себя: как отсортировать товары от дорогих к дешёвым, поменяв одну строку в compareTo?

Поменять местами аргументы: Integer.compare(other.price, this.price). Тогда «меньше» станет тот, у кого цена больше, и он окажется в начале списка.

7. Несколько интерфейсов и extends вместе с implements

Родитель у класса один, а интерфейсов — сколько угодно, через запятую:

public class Multi implements Notifier, Printable { ... }

Класс обязан реализовать методы всех перечисленных интерфейсов. Объект такого класса можно положить и в переменную Notifier, и в переменную Printable — каждая «видит» свой набор методов.

Если есть и родитель, и интерфейсы, порядок фиксированный: сначала extends, потом implements.

public class SavingsAccount extends BankAccount implements Comparable<BankAccount> { ... }   // ✓
public class Order implements Notifier extends Object { }   // error: '{' expected

Хорошая новость для домашки: если родитель реализует интерфейс, потомки реализуют его автоматически. Сделаешь BankAccount implements Comparable<BankAccount> — и SavingsAccount тоже станет сравнимым, ничего не дописывая. Это обычное наследование: метод compareTo унаследован.

8. Частые вопросы

Чем интерфейс отличается от абстрактного класса?

Абстрактный класс (abstract class) — класс, от которого нельзя создать объект и в котором часть методов может быть без тела. Отсюда и слова «is not abstract» в ошибке из раздела 3. Главная разница: у абстрактного класса могут быть поля и конструктор, он даёт потомкам общий код. Но родитель у класса один. Интерфейс — только договор, зато их можно реализовать сколько угодно. Правило на практике: нужен общий договор — интерфейс; нужен общий код и данные для очень похожих классов — абстрактный класс. В современном Java-коде интерфейсы встречаются намного чаще.

Oracle — Abstract Methods and Classes.

Я видел в интерфейсе метод с телом и словом default. Это как?

Начиная с Java 8 интерфейс может содержать default-метод с готовой реализацией. Классы получают его бесплатно и могут переопределить. Нужно в основном для того, чтобы добавлять методы в старые интерфейсы, не ломая все классы, которые их уже реализуют. Я проверил: такой метод может вызывать абстрактные методы того же интерфейса. Свои интерфейсы пока пиши без default.

Oracle — Default Methods.

Ты писал ArrayList<Product> cart = new ArrayList<>(). А я видел List<Product> cart = new ArrayList<>(). В чём разница?

Отличный пример этого урока в стандартной библиотеке: List — интерфейс («упорядоченная коллекция»), а ArrayList — один из классов, который его реализует. Переменная типа List — это как поле Notifier в OrderService: код зависит от договора, а не от конкретного класса. Так принято писать, и в уроке про коллекции мы перейдём на это.

Можно ли в интерфейсе объявить поле?

Только константу: всё, что объявлено в интерфейсе как переменная, автоматически public static final — одно значение на всех, менять нельзя. Хранить данные объекта интерфейс не умеет.

Может ли интерфейс наследовать другой интерфейс?

Да, через extends: interface UrgentNotifier extends Notifier. Классу, реализующему UrgentNotifier, придётся реализовать методы обоих.

Почему интерфейс не назвать INotifier, чтобы было видно, что это интерфейс?

Так принято в C#, а в Java — нет. Имя интерфейса описывает роль (Notifier, List), а реализация уточняет, как именно (SmsNotifier, ArrayList).

9. Проверь себя

Без подглядывания. Ошибся — вернись к разделу.

1. Чем интерфейс отличается от обычного класса?

Интерфейс описывает, какие методы должны быть у реализующих классов. Создать его объект нельзя, хранить данные объекта он не умеет. Методов может быть сколько угодно, реализаций — тоже.

2. Класс написал implements Notifier, но не написал метод send. Что будет?

Компилятор проверяет, что все методы интерфейса реализованы: ... does not override abstract method send(String,String) in Notifier.

3. Notifier n = new EmailNotifier("a@b.ru"); n.send("Илья", "Привет"); Какой send выполнится?

Правило 2: версия выбирается по объекту. У интерфейса тела нет, выполнять там нечего — поэтому всегда выполняется реализация класса.

4. Почему OrderService получает Notifier через конструктор, а не создаёт new SmsNotifier() сам?

Сервис не привязан к конкретному способу: снаружи можно передать SMS, email, фейк для проверки. Это внедрение зависимости — основа Spring.

5. Что должен вернуть a.compareTo(b), если a «больше» b?

Договор compareTo: отрицательное — this меньше, ноль — равны, положительное — больше. Возвращаемый тип int, не boolean.

Шаг 3. TransferService — сервис переводов

  1. Поле типа Notifier, получает его через конструктор. Сам new никакого уведомителя не делает.
  2. Метод transfer(BankAccount from, BankAccount to, int amount):
    • выполняет перевод через уже существующий transferTo;
    • при успехе отправляет два уведомления: отправителю «Списано N руб.», получателю «Зачислено N руб.»;
    • если не хватило денег — отправляет отправителю одно уведомление «Перевод не выполнен: …» с текстом исключения, и бросает исключение дальше (throw e; из частых вопросов урока 4). Сервис не должен «проглатывать» ошибку — решать, что с ней делать, будет вызывающий код.
