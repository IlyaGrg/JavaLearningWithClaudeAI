Git-ветки: работать, не ломая main

После этого урока ты сможешь делать задачу в отдельной ветке, сливать её в main, читать граф коммитов и безопасно выбрасывать неудачные эксперименты.

Зачем этот урок для backend. В команде никто не коммитит прямо в main. Каждая задача делается в своей ветке и попадает в main через слияние (обычно через pull request на GitHub). На собеседовании про ветки спрашивают почти всегда, а в первый рабочий день ты создашь ветку раньше, чем напишешь строчку кода.

А лично тебе ветки решат знакомую проблему: в уроках 7, 8 и 9 эксперименты оставались в коде. В ветке эксперимент можно выбросить одной командой, и main его даже не увидит.

Разминка: вспомни урок 9

1. Что даёт <T extends Comparable<T>> в объявлении max?

Обещание компилятору, что у T есть compareTo. Без него про T известно только, что это Object, и item.compareTo(best) не компилируется: cannot find symbol.

2. Почему в Bank метод getCount() лучше, чем getAccounts(), возвращавший репозиторий?

Через репозиторий можно было вызвать save в обход openAccount и подменить чужой счёт. Число «пересохранить» нельзя. Банк отдаёт наружу ровно то, что нужно, — это инкапсуляция из урока 3.

3. Ты закоммитил код, в выводе которого было две «ОШИБКА». Как Git помог бы, если бы баг нашёлся через неделю?

Коммиты — это снимки. По git log видно, когда изменился max, а git diff между коммитами покажет, какая строка. Сегодня добавим ещё одно правило: в main попадает только то, что прошло проверки. Ветки дают для этого место.

1. Что такое ветка

Каждый коммит хранит снимок проекта и ссылку на предыдущий коммит (родителя). Получается цепочка. Ветка — это просто подвижный указатель на один коммит (Pro Git, 3.1). Не копия файлов, не папка — файл размером 41 байт с номером коммита. Поэтому ветки создаются мгновенно.

A ← B ← C        ← main ← HEAD

Когда ты делаешь коммит, указатель текущей ветки сдвигается на новый коммит. HEAD — это «где я сейчас»: указатель на текущую ветку. Его показывает git status в первой строке («Текущая ветка: main»).

2. Создать ветку и переключиться

git switch -c fix-max      # создать ветку fix-max и сразу перейти в неё
Переключились на новую ветку «fix-max»

git branch                 # список веток, * — текущая
* fix-max
  main

Теперь два указателя смотрят на один коммит. Новый коммит сдвинет только fix-max:

A ← B ← C        ← main
         ↖
          D      ← fix-max ← HEAD

Вернуться — git switch main. Git заменит файлы в папке на снимок коммита C: исправления из D пропадут из IntelliJ. Они не потеряны, они в ветке fix-max. Переключишься обратно — вернутся.

switch или checkout? В старых статьях и в части Pro Git пишут git checkout -b fix-max. Это то же самое. git checkout умеет слишком много разного, поэтому в Git 2.23 для веток добавили отдельную команду git switch. Пользуйся ей, а checkout просто узнавай.

Незакоммиченные изменения переезжают с тобой

Ловушка: если ты поменял файл и не закоммитил, git switch перенесёт эти изменения в другую ветку (проверено):

git switch c1
Переключились на ветку «c1»
M	A.txt                     # изменение приехало вместе с тобой

А если тот же файл в другой ветке отличается, Git откажется переключаться:

error: Ваши локальные изменения в указанных файлах будут перезаписаны при переключении на состояние:
	Bank.java
Сделайте коммит или спрячьте ваши изменения перед переключением веток.
Прерываю

Правило: перед git switch — git status, и он должен быть чистым. Закоммить или откати (git restore файл).

3. Слияние: fast-forward

Работа в ветке готова, проверки ОК. Переходишь в ту ветку, куда сливаешь, и вызываешь git merge с той, откуда:

git switch main
git merge fix-max
Обновление a82a8d8..2accf07
Fast-forward
 Bank.java | 1 +
 1 file changed, 1 insertion(+)

В main новых коммитов не было, D просто «стоит дальше» по той же линии. Git ничего не объединяет, а сдвигает указатель main вперёд. Это называется fast-forward (перемотка):

A ← B ← C ← D    ← main, fix-max

Ветка больше не нужна — удали указатель (коммиты остаются в main):

git branch -d fix-max
Ветка fix-max удалена (была 2accf07).

4. Слияние двух линий: коммит слияния

Пусть ты сделал две ветки от одного коммита: a поменяла A.txt, b поменяла B.txt. Первая сольётся перемоткой. А для второй перемотать нельзя: main уже ушёл в другую сторону. Git сравнит обе линии с общим предком и создаст коммит слияния с двумя родителями (Pro Git, 3.2):

git merge a
Fast-forward ...
git merge b
Merge made by the 'ort' strategy.
 B.txt | 1 +

Без флага --no-edit Git откроет редактор с готовым сообщением «Merge branch 'b'». Сохрани и закрой его. Если открылся vim: Esc, потом :wq и Enter.

Посмотреть граф:

git log --oneline --graph --all
*   5b29014 Merge branch 'b'
|\
| * ff7dbc8 B
* | a5087fe A
|/
* 2accf07 Исправить max
* a82a8d8 Начало

Читай снизу вверх. * — коммит, линии — родители. От 2accf07 разошлись две линии, а 5b29014 их соединил. Эту команду стоит запускать после каждого слияния, пока граф не начнёт читаться с одного взгляда.

А если обе ветки поменяли одну строку?

Тогда Git не может выбрать сам — это конфликт. Подробно будем разбирать в январе, сейчас достаточно узнать его в лицо:

КОНФЛИКТ (содержимое): Конфликт слияния в Bank.java
Сбой автоматического слияния; исправьте конфликты, затем зафиксируйте результат.
<<<<<<< HEAD
b1                 ← версия текущей ветки (main)
=======
b2                 ← версия сливаемой ветки
>>>>>>> c2

Если увидел это и растерялся — git merge --abort вернёт всё как было до merge. Ничего не сломается.

5. Ветка для эксперимента

Вот решение для «сломай нарочно — убедись, что тест упал»:

git switch -c experiment/break-count
# ломаешь getCount(), запускаешь, видишь ОШИБКА
git commit -am "Сломать getCount для проверки тестов"
git switch main                        # в main всё целое
git branch -d experiment/break-count
error: the branch 'experiment/break-count' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D experiment/break-count'

Git защищает от потери коммитов: -d удаляет только слитую ветку. Ты уверен, что эксперимент не нужен, — значит -D (большая). Коммит со сломанным кодом исчезнет из истории, в main он не попадал никогда.

Косая черта в имени — просто соглашение, как папка: feature/…, fix/…, experiment/…. Так ветки удобно группировать.

6. Ветка на GitHub

Локальная ветка живёт только на твоём компьютере. Отправить её:

git push -u origin lesson0010
 * [new branch]      lesson0010 -> lesson0010
branch 'lesson0010' set up to track 'origin/lesson0010'.

-u нужен один раз: он связывает локальную ветку с удалённой, дальше хватает просто git push. На GitHub появится переключатель веток и кнопка «Compare & pull request». Pull request — это просьба влить ветку в main, на которой коллеги делают ревью (GitHub Docs). Его будем делать в январе, пока только посмотри на кнопку.

Типичный рабочий цикл

git switch main
git status                         # чисто?
git switch -c feature/что-делаю
...код, проверки, git commit...    # сколько угодно коммитов
git switch main
git merge feature/что-делаю
git log --oneline --graph --all
git branch -d feature/что-делаю
git push

Проверь себя

1. Что такое ветка в Git?

Ветка — указатель на коммит, файл с его номером. Поэтому создаётся мгновенно и ничего не копирует.

2. В main после создания fix новых коммитов не было. Что сделает git merge fix, запущенный в main?

Fast-forward: коммиты fix уже стоят «после» main на одной линии, объединять нечего.

3. Обе ветки получили свои коммиты, в разных файлах. Что сделает git merge?

Перемотать нельзя — линии разошлись. Git объединяет изменения и записывает коммит слияния, у которого два родителя.

4. В ветке experiment есть коммит, которого нет в main. Что ответит git branch -d experiment?

-d защищает от потери работы. Удалить несмотря ни на что — -D.

5. Ты поменял Main.java, не закоммитил и вызвал git switch main. В main этот файл такой же, как в твоей ветке. Что будет?

Незакоммиченное не принадлежит никакой ветке и едет с тобой. Отказ будет, только если файл в двух ветках различается. Поэтому перед switch — чистый git status.

Домашка

Код этой домашки — продолжение банка. Все Git-команды делай в терминале (не кнопками IntelliJ), чтобы видеть их ответы. Ответы на вопросы и вывод команд записывай в src/lesson0010/GIT-NOTES.md.

Шаг 1. База в main

Убедись, что git status чистый и ты в main. Скопируй src/lesson0009 в src/lesson0010, поменяй package, проверь, что все 16 проверок ОК. Закоммить прямо в main: это стартовая точка.

Шаг 2. Ветка refactor/repository

Создай ветку и в ней приведи в порядок InMemoryRepository: existsById и findAll в одну строку, сообщение «нельзя невозможно», понятное имя исключения вместо BadRequestByIdException (переименовывай без галочки «Search in comments and strings»). Проверки ОК — коммит. Можно несколькими коммитами.

Шаг 3. Ветка feature/currency-checks — от main!

Предскажи до команды и запиши: что ты увидишь в InMemoryRepository.java после git switch main? Переключись, проверь.

Создай от main вторую ветку. В ней — только Main.java: проверки для валют (count, existsById для есть/нет, findById отсутствующего бросает исключение). Коммит.

Ловушка: если на шаге 2 ты переименовал исключение, в этой ветке его старое имя. Это нормально — ветки ещё не знают друг о друге. Ловить в проверке лучше RuntimeException или старое имя; после слияния исправишь.

Шаг 4. Слить обе ветки в main

Предскажи до команд: какое из двух слияний будет fast-forward, а какое создаст коммит слияния? Почему? Потом слей refactor/repository, затем feature/currency-checks. Скопируй в заметки вывод обоих merge и git log --oneline --graph --all.

После слияния скомпилируй и запусти: все проверки должны быть ОК. Если не компилируется из-за имени исключения — поправь и закоммить в main. Удали обе ветки через -d.

Обе ветки могли задеть Main.java (переименование исключения меняет и catch). Если Git написал «КОНФЛИКТ» — не паникуй: git merge --abort и напиши мне, разберём вместе. Это будет первый конфликт раньше плана, и это даже хорошо.

Шаг 5. Эксперимент, который нельзя забыть откатить

Ветка experiment/break-max: сломай max (верни < 0), запусти, запиши, какие проверки упали. Закоммить. Перейди в main, запусти снова — запиши, что вывелось. Удали ветку сначала через -d (запиши ошибку), потом через -D.

Шаг 6. На GitHub

git push для main. Дополнительно: создай ветку lesson0010-notes, закоммить в неё заметки, отправь через git push -u origin lesson0010-notes, найди её на GitHub и посмотри на кнопку «Compare & pull request» (PR не создавай). Потом слей её в main локально и снова git push.
